01. 브라우저: URL 입력부터 픽셀까지

1-1. 큰 그림: URL에서 화면의 픽셀까지

브라우저 렌더링은 HTML을 화면에 그냥 출력하는 일이 아니다. 문서를 해석하고(DOM), 스타일 규칙을 계산하고(CSSOM/Computed Style), 배치와 그리기 정보를 만든 뒤, 최종 화면을 합성하는 과정이다.

필수 주의점 3개

  1. 위 도식은 논리적 개념도다. 네트워크 요청, HTML의 점진적 파싱, CSS 다운로드와 이미지 디코딩은 겹칠 수 있다. 파이프라인을 항상 하나의 완벽한 순차 절차로 생각하면 안 된다.
  2. DOM + CSSOM → Render Tree는 학습용 설명이다. 실제 Chromium 등의 구현은 스타일·레이아웃·페인트 객체와 레이어 구성 단계가 더 복잡하다.
  3. 최초 페이지 표시와 스크롤·클릭·애니메이션으로 인한 프레임 갱신은 구별한다. 매번 DOM과 CSSOM을 처음부터 전부 만들지 않고, 변경 영향이 있는 단계부터 다시 계산할 수 있다.

최상위 면접 질문: "HTML을 받은 순간부터 첫 픽셀이 화면에 나타날 때까지 어떤 일이 일어나며, 그 과정에서 JS/CSS가 어디를 막을 수 있나요?"

모범 답변 · 약 60초

“브라우저가 HTML을 수신하면 파싱해 DOM을 만들고, CSS 파일을 받아 CSSOM과 적용 스타일을 계산합니다. 화면에 실제로 필요한 요소들의 시각 구조를 만든 다음 Layout에서 크기와 위치를 결정하고, Paint에서 그릴 내용을 준비합니다. 래스터화와 합성을 거쳐 화면이 표시됩니다.

이때 일반적인 스타일시트는 렌더링을 지연시킬 수 있지만 HTML 파서를 직접 멈추는 것은 보통 아닙니다. 반면 async/defer 없는 고전 스크립트는 HTML 파서를 중단하고 실행합니다. 이 스크립트는 앞서 발견한 스타일시트가 아직 로딩 중이면 그 스타일시트도 기다릴 수 있어 결과적으로 파싱이 더 늦어집니다. 따라서 렌더링 필수 CSS와 동기 JS를 줄이고, Network와 Performance 패널에서 실제 병목을 확인합니다.”

심화 해설 · 실제 순서, 차단 지점, 흔한 오답, 꼬리 질문

① 첫 화면까지의 개념적 순서. 문서 응답의 바이트를 해석하면서 HTML 토큰화·DOM 생성을 진행한다. 리소스 발견 시 CSS·JS 다운로드가 병행되며, CSS 규칙을 해석해 CSSOM을 만들고 계산된 스타일을 결정한다. 렌더링에 필요한 시각 구조를 기준으로 Layout에서 기하 정보, Paint에서 그리기 작업을 준비한다. 래스터화한 결과를 합성해 프레임을 표시한다. 전체 HTML 수신이나 이미지 전부 다운로드가 항상 선행되어야 하는 것은 아니다.

② CSS는 어디를 막나? 렌더링에 필요한 스타일시트는 초기 화면에 잘못된 스타일이 잠깐 나타나는 것을 피하도록 렌더링을 지연시킬 수 있다. 일반적으로 CSS 다운로드만으로 HTML 파싱이 멈추지는 않는다. 다만 CSS 앞뒤에 있는 스크립트 로딩 순서 및 렌더링 차단 여부에 따라 간접 영향이 달라진다.

③ JS는 어디를 막나? <script src="legacy.js"></script> 같은 일반 고전 스크립트는 HTML 파서가 해당 위치에서 실행을 기다린다. defer는 파싱과 병렬 다운로드 후 파싱이 끝난 뒤 순서대로 실행되며, 일반적인 모듈 스크립트도 지연 실행된다. async는 준비된 순간 실행되어 순서가 보장되지 않고 파싱 도중 실행된다면 파싱을 잠시 중단시킬 수 있다.

④ CSS와 JS의 교차 효과. 일반적인 동기 스크립트는 이전 스타일시트의 로딩 완료를 기다릴 수 있다. 따라서 느린 CSS → 동기 JS 실행 지연 → HTML 파서 재개 지연이 생길 수 있다. 중요한 건 CSS가 무조건 파서를 막는다는 뜻이 아니라, 스크립트 의존 관계로 간접적인 지연이 생긴다는 점이다.

⑤ 첫 픽셀과 이벤트를 혼동하지 말 것. 첫 페인트(First Paint)는 콘텐츠 표시를 뜻하는 FCP와 다르다. DOMContentLoaded는 문서 파싱 및 지연 스크립트 완료에 관한 이벤트이고, load는 이미지 등 의존 리소스 완료까지 고려한다. 페이지 구조·스타일에 따라 실제 화면 표시 시점은 이벤트들과 반드시 일치하지 않는다.

⑥ 검증 방법. Network의 Waterfall과 요청 우선순위로 CSS/JS 지연을 확인한다. Performance에서 Parse HTML, Evaluate Script, Recalculate Style, Layout, Paint, FCP 마커를 찾아 실행·렌더링의 병목을 구분한다. 캐시·네트워크 조건을 고정하고 수정 전후를 비교한다.

면접에서 피할 오답

“CSS가 HTML 파싱을 항상 중지한다”, “defer 스크립트는 네트워크 요청이 느리면 동기 스크립트와 같다”, “DOMContentLoaded가 발생하면 반드시 화면이 전부 보인다”, “Render Tree는 모든 DOM 노드의 단순 복사다”는 부정확하다.

꼬리 질문 · CSS가 느리면 스크립트 없는 페이지도 화면이 늦어지나요? 네. 렌더링에 필수적인 스타일시트는 초기 페인트의 선행 조건이 될 수 있기 때문이다. HTML 파싱과 렌더링은 구별해야 한다.

참고 원문: MDN 브라우저 동작, web.dev Critical Rendering Path, MDN DOMContentLoaded.

차단 지점을 실제 코드로 읽어보기

  • critical.css: 렌더링에 필요한 스타일시트라면 화면 표시 지연 가능. 그 자체가 일반적으로 HTML 파싱을 멈추는 것은 아님.
  • legacy.js: HTML 파싱 중단. 앞선 스타일시트가 아직 준비되지 않았다면 그 로딩도 기다릴 수 있음.
  • app.js: HTML 파싱과 다운로드 병행. 파싱이 끝난 뒤 실행되며 DOMContentLoaded보다 먼저 완료되어야 함.
  • h1: 이미 처리한 DOM과 스타일 조건이 갖춰지면 화면 표시 가능. load 이벤트를 반드시 기다리는 것은 아님.

1-2. Navigation과 HTML 스트리밍: 렌더링 이전에도 병목이 있다

  1. 주소를 해석하고, 현재 문서 전환·리다이렉트·캐시·서비스 워커 개입 여부 등을 확인한다.
  2. 필요하면 DNS 조회와 연결 수립을 진행한다. 환경에 따라 TCP/TLS 또는 QUIC(HTTP/3)을 사용한다.

  5. 브라우저의 preload scanner 등은 HTML 파서와 별개로 발견 가능한 하위 리소스를 미리 요청하여 다운로드 시간을 줄일 수 있다.

핵심: CSS는 보통 HTML 파서를 직접 멈추지 않지만, 렌더링에 필요한 스타일 계산을 지연시킬 수 있다. 또한 동기 JS는 최신 스타일 정보를 필요로 할 수 있어, 앞서 로딩 중인 스타일시트 때문에 실행이 늦어질 수 있다. "CSS가 HTML 파싱을 무조건 차단한다"는 답변은 부정확하다.

1-3. DOM·CSSOM·Render Tree: 세 가지를 확실히 구분하기

다음 예시를 보자.

  • DOM(Document Object Model): HTML을 해석한 문서 객체 트리. p.hidden 요소도 DOM에 존재한다. JavaScript는 document.querySelector('.hidden')으로 접근 가능하다.
  • CSSOM(CSS Object Model): CSS 선언·규칙을 브라우저가 다룰 수 있는 구조로 해석한 모델이다. 실제 요소에 적용되는 값은 선택자 일치, 상속, 캐스케이드, 사용 가능한 스타일 정보 등을 고려해 계산된다.
  • Render Tree / 레이아웃에 쓰이는 시각 트리: 화면에 배치·그리기할 대상과 그에 적용된 스타일을 표현하는 학습용 개념. display: none은 일반적인 박스를 생성하지 않아 배치 대상에서 빠진다. ::before 같은 생성 콘텐츠는 화면에 나타날 수 있다.

세 가지 자주 틀리는 비교

CSS DOM에 존재? 레이아웃 공간? 보이는가?
display: none 예 없음 아니오
visibility: hidden 예 있음 아니오
opacity: 0 예 있음 시각적으로 투명하나 상호작용 가능할 수 있음

opacity: 0을 display: none 대신 쓸 때는 접근성·포커스·포인터 이벤트까지 고려해야 한다. 실제 구현에서 DOM과 렌더링 내부 구조는 일대일 대응이 아니다.

1-4. Style 계산: CSS의 최종 값은 어디서 결정되는가?

브라우저는 선택자에 해당하는 규칙을 찾고, 캐스케이드(출처·중요도·레이어·우선순위·소스 순서 등), 상속, 지정값/계산값을 바탕으로 각 요소에 적용될 스타일을 결정한다. width: 50%처럼 부모 크기를 알아야 최종 배치 값이 정해지는 속성도 있으므로 "계산된 스타일 = 최종 픽셀 크기"가 항상 성립하지는 않는다.

#main .card가 실제로 일치한다면 color에 대해 우선하는 것이 일반적이다(같은 출처/중요도/레이어라는 전제). 하지만 사용자 스타일, !important, cascade layer 등까지 무시하고 "ID가 언제나 이긴다"고 설명하면 안 된다.

1-5. Layout: 보이는 상자의 크기와 위치를 계산한다

Layout(레이아웃, 과거 표현 reflow)은 스타일을 기준으로 각 박스의 크기·위치·줄바꿈·부모 자식 관계 등을 계산하는 단계다. width, font-size, display, 텍스트 길이, 뷰포트 너비 등이 변경되면 레이아웃에 영향이 생길 수 있다.

  • 부모 크기가 달라지면 자식의 %, flex, grid 배치도 영향을 받을 수 있다.
  • 글꼴 변경으로 글자 폭이 달라지면 줄바꿈과 블록 높이가 달라질 수 있다.
  • 위치가 바뀌어도 다른 박스 배치에 영향이 없다면 재계산 범위는 작을 수 있다. 변경이 전체 문서 Layout을 무조건 유발하는 것은 아니다.

getBoundingClientRect(), offsetWidth, offsetHeight 등의 값을 읽기 전에 스타일 변경이 쌓여 있다면, 브라우저가 정확한 값을 주기 위해 강제 동기 레이아웃(forced layout)을 수행해야 할 수 있다.

1-6. Paint → Rasterization → Composite: 화면에 색이 생기는 과정

  • Paint(페인트): 배경, 텍스트, 테두리, 그림자 등 어떻게 그릴지를 그리기 명령/디스플레이 리스트 형태로 준비한다.
  • Rasterization(래스터화): 그리기 명령을 실제 픽셀/타일 데이터로 변환한다. 일부 작업은 별도 래스터 스레드·GPU 등을 활용할 수 있다.
  • Composite(합성): 필요한 레이어와 타일을 적절한 순서 및 변형으로 결합하여 최종 프레임을 표시한다.

transform/opacity 변경은 요소가 적절히 합성 레이어로 처리되는 조건에서는 Layout·Paint 작업을 건너뛰고 합성 단계 위주로 처리될 수 있다. 하지만 항상 GPU에서 실행되거나 항상 레이어가 새로 생기는 것은 아니다. 과도한 will-change는 메모리 사용량을 늘릴 수 있다.

브라우저 구현 주의: Layout·Paint·Rasterization·Composite를 구분하는 것은 좋은 학습법이지만, 브라우저 엔진별 레이어화·스레드·래스터 처리의 세부 순서는 다르다.

1-7. 초기 렌더링과 이후 프레임 갱신의 차이

초기 로딩은 HTML → DOM, CSS → CSSOM이 핵심이지만, 이후 애니메이션/인터랙션은 대략 다음 루프에서 필요한 부분만 처리한다.

60Hz 모니터는 한 번의 화면 갱신 주기가 약 16.7ms, 120Hz는 약 8.3ms다. 이 시간 전체를 JavaScript 실행에 쓸 수 있다는 뜻은 아니며, 실제 목표는 입력 처리·스타일·레이아웃·페인트·합성의 병목을 줄이는 것이다.

requestAnimationFrame은 다음 페인트 이전에 실행할 콜백을 예약하는 API이지, 콜백 직후 반드시 화면이 즉시 칠해진다는 보장은 아니다. 오래 걸리는 JS 작업은 프레임 갱신 기회를 막을 수 있다.

1-8. CSS 속성에 따라 왜 비용이 달라질까?

변경 내용 흔한 렌더링 영향 실전 판단
width, height, padding, font-size Style → Layout → Paint → Composite 주변 요소까지 배치가 달라질 수 있음
color, background-color, box-shadow Style → Paint → Composite 위치 재계산 없이 다시 그릴 수 있으나 페인트 영역 확인
transform, opacity Style → Composite 중심이 가능 레이어·애니메이션 조건에 따라 Paint/레이어화 비용이 발생할 수 있음
display: none 토글 트리/Style/Layout 갱신 가능 요소가 배치에서 사라지고 주변 배치가 변함
텍스트 내용 변경 Style/계산된 레이아웃 → Paint 가능 글자 폭이 바뀌면 줄바꿈과 크기 변동 가능

공식처럼 외우지 말 것: 표는 '흔한 경향'이다. 브라우저 버전, 해당 요소의 레이어 상태, 인접 요소, 애니메이션 방식에 따라 실제 수행 단계가 달라진다. DevTools의 Performance로 검증한다.

1-9. 실무 사례: Layout Thrashing(레이아웃 스래싱)

DOM의 쓰기 → 읽기 → 쓰기 → 읽기를 반복하면 브라우저가 지연해 두었던 레이아웃 작업을 중간중간 강제로 실행할 수 있다.

측정 값과 스타일 갱신의 실제 영향 범위를 점검해야 한다. DOM 조작 횟수가 많다는 사실만으로 느린 이유가 확정되는 건 아니다. 값 캐싱, 배치 읽기/쓰기, CSS 애니메이션, 가상화 등의 수단을 상황에 맞게 선택한다.

1-12. DevTools로 원인 추적하는 절차

  2. Performance: 느린 동작을 재현하며 녹화하고, Main thread의 Long task / Recalculate Style / Layout / Paint 이벤트를 찾는다.
  3. Rendering: Paint flashing, Layout Shift Regions로 화면상 재칠하기·이동을 확인한다.
  4. Elements → Computed: 실제 적용 스타일을 확인하고, 레이아웃에 영향을 준 속성을 좁힌다.
  5. 최적화 후 재측정: 동일 조건에서 개선 전/후 시간을 비교하고, 다른 UI 기능이 깨지지 않았는지 확인한다.

  3. width와 transform: scale()의 시각적 변화가 비슷한데 애니메이션 비용이 다를 수 있는 이유는?
  4. requestAnimationFrame 콜백 안에서 offsetWidth를 읽으면 언제 강제 레이아웃이 일어날 수 있는가?
  5. React 컴포넌트가 다시 렌더링되면 브라우저 Layout/Paint도 반드시 실행되는가?
  6. LCP와 DOMContentLoaded 중 어떤 것이 "사용자가 큰 콘텐츠를 본 시점"에 더 가까운가?
개념 체크 정답 / 해설 보기
  1. 둘 다 DOM에는 존재한다. display:none은 일반적인 레이아웃 공간을 만들지 않지만 visibility:hidden은 공간이 유지된다.
  2. 일반적으로 CSS 로드 자체는 HTML 파싱을 멈추지 않는다. 하지만 스타일 정보가 필요한 앞선 동기 스크립트 실행을 지연시킬 수 있고, 그로 인해 파싱이 지연될 수 있다.
  3. width는 배치 크기에 영향을 주기 쉽지만 transform은 합성 단계로 처리할 여지가 있다. 다만 조건별 DevTools 확인이 필요하다.
  4. 이전 스타일 변경으로 레이아웃이 무효화되어 있고, 브라우저가 최신 실제 크기를 계산해야 할 때 강제 동기 Layout이 가능하다.
  5. 아니다. React render는 가상 UI 계산이고 commit에서 DOM 변경을 적용한다. 실제로 변한 DOM/스타일이 없으면 브라우저의 레이아웃/페인트 작업도 없을 수 있다.
  6. LCP가 더 직접적이다. DOMContentLoaded는 파싱/지연 스크립트 이벤트이지 실제 콘텐츠 페인트 지표가 아니다.

2-1. 시맨틱 요소가 중요한 이유

div만으로도 비슷한 화면을 만들 수 있지만, header, nav, main, article, section, aside, footer는 구조 의미를 제공한다. 모든 section에 제목을 넣는 것이 이해를 돕고, 클릭하는 동작은 원칙적으로 버튼을 쓴다.

2-2. button 대 div onClick

버튼은 기본적으로 키보드 조작, 포커스 가능성, 역할 전달, 비활성화 등의 의미가 내장되어 있다. div에 클릭만 달면 이 기능을 직접 재구현해야 한다. 링크는 이동, 버튼은 동작을 나타낸다.

  • <a href="...">: 새 위치·문서로 이동.
  • <button type="button">: 현재 화면에서 동작 수행.
  • <button type="submit">: 폼 전송. 폼 안 버튼은 기본값이 submit이므로 의도 확인.
  • disabled: 상호작용 및 일반 포커스 이동 차단. 단순히 aria-disabled만 설정하면 동작 차단은 직접 구현해야 한다.

2-3. 폼과 유효성 검증

클라이언트 검증은 UX, 서버 검증은 무결성/보안 경계다. 프론트 검증만으로 안전하다고 판단하면 안 된다.

2-4. 접근성 4원칙

인식 가능(Perceivable) / 운용 가능(Operable) / 이해 가능(Understandable) / 견고함(Robust). 색만으로 오류를 나타내지 않고, 키보드로 모든 조작을 수행할 수 있게 하며, 폼 레이블과 오류 메시지를 연결한다. 이미지 alt는 정보성 이미지에는 의미, 장식용에는 빈 문자열이 일반적이다.

03. CSS: 레이아웃이 깨지는 정확한 이유

3-1. 캐스케이드와 우선순위

일반적인 상황에서 선언은 출처·중요도·cascade layer·specificity·소스 순서 등을 함께 평가한다. !important를 많이 붙이는 방식은 유지보수 비용을 키운다. specificity는 (ID, class/attribute/pseudo-class, type/pseudo-element)로 비교한다. :where()는 specificity가 0이다.

3-2. Box model과 box-sizing

기본 content-box에서 CSS width는 내용 영역만 뜻하고 padding/border는 바깥에 추가된다. border-box는 지정 width 안에 padding/border가 포함된다.

3-3. Flex: 왜 min-width: 0인가?

Flex 항목은 기본적으로 자동 최소 크기 때문에 내용보다 작아지지 않을 수 있다. min-width: 0(수평축), min-height: 0(수직축)을 상황에 맞게 지정해야 텍스트 말줄임/스크롤이 동작한다.

  • flex: 1은 상황에 따라 flex-grow:1; flex-shrink:1; flex-basis:0%로 해석되는 흔한 축약이다. 축소 기준/가용 공간 개념까지 설명하자.
  • align-items는 교차축, justify-content는 주축 기준이다. flex-direction이 바뀌면 주축도 바뀐다.
  • Grid는 2차원 레이아웃, Flex는 1차원 흐름을 우선할 때 유리하다.

3-4. Grid와 반응형

auto-fit은 빈 트랙을 접을 수 있고, auto-fill은 빈 트랙도 유지할 수 있다. 미디어 쿼리는 뷰포트, 컨테이너 쿼리는 부모 컨테이너 크기를 기준으로 구성요소를 적응시킨다.

3-5. position·stacking context·z-index

z-index: 999999를 늘려도 해결되지 않는 이유는 부모 stacking context를 넘을 수 없기 때문이다. position과 z-index, transform, opacity<1 등은 조건에 따라 새로운 stacking context를 만든다. 모달·팝오버·툴팁은 포털/최상위 레이어 전략도 검토한다.

3-6. BFC, margin collapse, overflow

Block Formatting Context는 float 간섭과 마진 동작 등에 영향 준다. display: flow-root로 독립 BFC를 만들 수 있다. 수직 마진 병합은 형제/부모 관계와 레이아웃 모드에 따라 일어나거나 발생하지 않는다. Flex/Grid 항목 사이에는 일반적인 인접 블록 마진 병합이 없다.

3-7. CSS 디버깅 순서

  1. 해당 요소 선택 → Computed에서 최종 값 확인.
  2. 적용된 규칙이 취소선인지, 상속/레이어 때문인지 확인.
  3. Box model에서 width/padding/border 실측.
  4. 부모의 overflow, stacking context, containing block 확인.
  5. 문제를 20줄짜리 최소 재현 코드로 줄인다.

04. JavaScript I: 타입·스코프·실행 컨텍스트

4-1. JS 데이터 모델

원시값: string, number, bigint, boolean, undefined, symbol, null (단, typeof null === 'object'는 역사적 특성). 나머지 일반 객체는 참조를 통해 다룬다. 원시값/객체를 ‘스택/힙에 반드시 이렇게 저장한다’고 언어 명세가 보장하지 않는다. 엔진 구현과 JS의 값 의미론을 구분한다.

4-2. 얕은 복사와 불변 업데이트

structuredClone은 복제 가능한 다양한 내장 자료형을 지원하지만, 함수 등은 복제 불가능, 사용자 정의 클래스의 모든 행위까지 그대로 보장하지 않는다. 모든 상태 변경에 만능 해법은 아니다.

4-3. ==, ===, Object.is

식 결과 이유
0 == false true 느슨한 비교의 형변환
0 === false false 타입이 다름
NaN === NaN false NaN의 특수 비교
Object.is(NaN, NaN) true SameValue
Object.is(0, -0) false +0/-0 구별
null == undefined true 느슨한 비교의 특별 규칙

규칙: 대부분 ===로 비교한다. 단, value == null을 null/undefined 동시 체크라는 명시적 의도로 쓰는 코드도 존재한다.

4-4. 스코프와 TDZ

var 선언과 함수 선언은 서로 다른 초기화 규칙이 있다. let/const도 선언 정보는 생성되지만 선언문에 도달하기 전에는 TDZ(Temporal Dead Zone)로 접근할 수 없다. '호이스팅이 없다'라고 단정하는 설명은 부정확하다.

4-5. 실행 컨텍스트·콜 스택

함수 호출 시 실행 컨텍스트가 만들어지고 스택에 쌓인다. 내부적으로 변수 환경/렉시컬 환경과 this 관련 정보 등을 다룬다. 재귀가 너무 깊으면 최대 호출 스택 초과가 발생한다. 동기 함수는 끝나기 전까지 다음 동기 호출 흐름을 막는다.

4-6. Truthy·Falsy와 ??

거짓 값은 false, 0, -0, 0n, NaN, '', null, undefined 등이다. 빈 배열과 빈 객체는 truthy다. ??와 ||를 혼동하면 0이나 빈 문자열을 의도치 않게 덮어쓴다.

06. JavaScript III: 이벤트 루프·비동기·경쟁 상태

6-1. 실행 순서의 원칙

  1. 현재 동기 콜 스택의 코드를 실행한다.
  2. 한 task가 끝나고 스택이 비면, 마이크로태스크 큐를 비울 때까지 실행한다.
  3. 브라우저는 적절한 시점에 렌더링 기회를 얻고, 다음 task를 처리한다.

Promise.then, queueMicrotask는 마이크로태스크를 예약한다. setTimeout은 task를 예약한다. 타이머 0ms는 즉시 실행 보장이 아니다.

6-2. async/await의 실제 의미

async 함수는 Promise를 반환한다. await는 해당 비동기 함수의 나머지 부분 실행을 일시 중단하고 Promise 결과가 정해지면 마이크로태스크 흐름에서 재개한다. 메인 스레드 전체를 멈추지는 않는다.

6-3. 순차 요청과 병렬 요청

Promise.all은 하나라도 거부되면 결과 Promise가 거부된다. 나머지 요청을 자동으로 취소하는 것은 아니다. 부분 실패를 수집하려면 Promise.allSettled를 검토한다.

6-4. fetch와 에러 처리

fetch는 HTTP 404/500을 받았다고 Promise를 자동으로 reject하지 않는다. 네트워크 실패, 중단 같은 상황과 HTTP 오류 상태를 구분해야 한다.

6-5. 자동완성: 요청 경쟁(race condition) 해결

사용자가 're'를 입력하고 'react'를 입력했는데 앞의 요청이 늦게 돌아오면 이전 결과가 최신 UI를 덮을 수 있다. 취소 + 최신 응답만 반영이 안전하다.

참고: AbortController는 클라이언트의 요청 처리를 중단하는 도구이지, 서버가 이미 수행 중인 작업까지 반드시 되돌린다는 보장은 없다.

6-6. Debounce vs throttle

  • Debounce: 마지막 입력 이후 일정 시간 침묵하면 1회 실행. 검색어 API 요청.
  • Throttle: 일정 간격 내 실행 빈도를 제한. 스크롤/드래그 위치 업데이트.
  • requestAnimationFrame: 화면 갱신 주기에 맞춰 시각적 업데이트를 예약한다.

7-1. 이벤트 전파 단계

08. 네트워크·HTTP·인증·캐시

8-1. HTTP 메서드·상태 코드

  • GET 조회: 안전(safe), 멱등(idempotent). 민감 정보는 URL 쿼리에 노출되지 않도록 주의.
  • POST 생성/처리: 일반적으로 멱등 보장 없음. 결제·중복 제출은 서버의 idempotency key 등의 설계가 필요.
  • PUT 자원 전체 대체의 의미로 흔히 사용; 멱등.
  • PATCH 부분 변경; 항상 멱등인 것은 아니다.
  • DELETE 멱등 의미를 갖지만 첫 삭제와 두 번째 삭제의 상태 코드가 같아야 한다는 뜻은 아니다.

200 OK, 201 Created, 204 No Content, 301/308, 304 Not Modified, 400 Bad Request, 401 Unauthorized(인증 필요), 403 Forbidden, 404 Not Found, 409 Conflict, 429 Too Many Requests, 500, 502, 503을 설명할 수 있어야 한다.

8-2. CORS는 서버 접근 제어 자체가 아니다

CORS는 브라우저가 교차 출처 요청의 응답을 프론트 JS에 노출해도 되는지 결정하는 보안 메커니즘이다. curl/서버 간 요청은 같은 방식으로 제약되지 않는다. 서버의 인증·인가를 CORS로 대체해서는 안 된다.

  • Origin: scheme + host + port.
  • Preflight: 특정 비단순 요청 전에 OPTIONS로 허용 메서드·헤더 등을 점검한다.
  • Credentials: 쿠키 등의 자격 증명 포함 시 Access-Control-Allow-Origin: *과 자격증명 허용을 함께 쓰면 안 된다.

8-3. 쿠키 기반 인증과 토큰 기반 인증

쿠키 세션: 서버가 세션 상태(혹은 대응 검증 정보)를 관리하고, 브라우저가 조건에 맞는 쿠키를 자동 전송. HttpOnly, Secure, SameSite, CSRF 방어 설계가 중요하다.

Bearer access token: 보통 Authorization 헤더로 전송. 탈취되면 재사용 가능하므로 수명·보관·폐기·권한 검증이 중요하다. JWT라는 포맷만으로 안전한 것은 아니다.

중요: 프론트에 어떤 토큰을 저장하든 XSS 대응은 핵심이다. HttpOnly는 JS의 쿠키 읽기를 막지만, 동일 출처에서 실행되는 악성 스크립트의 요청 자체를 모두 막아주지는 않는다.

8-4. HTTP 캐싱

위 정책은 해시가 포함된 정적 자산에 적합한 경우가 많다. HTML 문서에 무조건 장기 캐시를 걸면 새 배포가 보이지 않을 수 있다.

no-cache는 '저장하지 말라'가 아니라 재사용 전에 검증하라는 의미다. no-store는 저장을 금지하려는 의도에 가깝다. ETag/If-None-Match로 조건부 요청 후 304가 가능하다. private는 공유 캐시에 저장하지 말라는 지시다.

8-5. 재시도 정책

GET 재시도는 비교적 단순하지만 서버가 과부하 상태라면 지수 백오프 + 지터가 필요하다. POST는 멱등 키가 없으면 자동 재시도로 중복 처리가 발생할 수 있다. 429/503의 Retry-After도 고려한다.

09. TypeScript: 런타임을 이해하는 타입 설계

9-1. TS는 런타임 타입 검증기가 아니다

TS 타입은 일반적으로 컴파일 단계에서 사라진다. 서버의 JSON, localStorage, URL 쿼리는 런타임 데이터다. as User는 검증이 아니라 타입 단언이다.

9-2. any vs unknown vs never

  • any: 타입 검사를 사실상 우회. 빠르지만 오류 전파가 커진다.
  • unknown: 어떤 값이든 받을 수 있으나 검증 전에는 사용 제한.
  • never: 도달 불가능한 경우/값이 없는 타입. 누락된 분기 검출에 유용.

9-3. 판별 유니온으로 불가능한 상태 제거

isLoading: boolean, data?: T, error?: string를 각각 둔다면 '로딩인데 동시에 에러이면서 데이터 있음' 같은 조합을 타입으로 표현하게 된다. 상태 머신 관점에서 유니온이 낫다.

9-4. 제네릭과 타입 추론

제네릭은 타입 간 관계를 보존하려고 쓴다. 모든 함수에 제네릭을 붙이는 것이 목표가 아니다.

9-5. 타입 유틸리티·좁히기

Partial, Required, Pick, Omit, Readonly, Record, ReturnType, Parameters, Awaited를 맥락에 맞게 사용. typeof, in, 판별 속성, 사용자 정의 type guard 등으로 narrowing한다.

9-6. satisfies, as const, 런타임 경계

as const는 리터럴 타입을 좁히고 readonly 성질을 유도한다. satisfies는 지정 타입과의 적합성을 확인하면서 표현식의 구체적인 추론 정보를 보존한다.

10. React: 렌더링 모델부터 다시 이해하기

10-1. 렌더는 화면 변경과 동의어가 아니다

React에서 render phase는 컴포넌트를 호출해 어떤 UI가 필요한지 계산하는 과정이다. commit phase에서 필요한 DOM 변경을 적용한다. 개발 모드 Strict Mode에서 일부 로직이 추가 호출될 수 있으므로 렌더 중 순수성을 유지해야 한다.

10-2. 상태는 스냅샷: 함수형 업데이트

setter 호출 직후 기존 렌더의 지역 변수 count가 즉시 바뀌는 것은 아니다. 다음 렌더에서 갱신된 값을 받는다.

10-3. key는 순서 표시가 아니라 정체성

리스트의 key는 React가 항목의 정체성을 추적하는 데 사용한다. 정렬·삽입·삭제가 있는 리스트에서 인덱스를 key로 쓰면 잘못된 로컬 상태가 다른 행에 붙는 문제가 발생한다.

key를 바꾸면 컴포넌트의 로컬 상태를 리셋하는 데도 사용할 수 있다. key는 자식에게 일반 prop으로 전달되지 않는다.

10-4. useEffect는 계산용이 아니다

외부 시스템(구독, 타이머, 네트워크, DOM API 등)과 동기화할 때 effect를 검토한다. 기존 props/state로 계산 가능한 값은 렌더에서 계산하는 편이 단순하다.

10-5. Effect의 cleanup

Effect는 의존성이 바뀌기 전 정리가 필요한 경우 cleanup을 실행하고, 컴포넌트가 해제될 때도 정리한다. 개발 모드에서는 문제를 드러내기 위해 setup/cleanup을 추가로 수행할 수 있다.

10-7. memo·useMemo·useCallback

이 최적화들은 정확성 도구가 아니라 렌더/계산 비용 최적화 수단이다. 적용 비용과 복잡성이 있으므로 React DevTools Profiler로 병목을 확인하고 사용한다. 일반적으로 부모가 렌더될 때 자식 함수도 다시 호출될 수 있지만, 그것이 항상 실제 DOM을 변경한다는 뜻은 아니다.

  • 여러 형제의 일관된 상태가 필요하면 공통 부모로 끌어올린다.
  • Context는 prop 전달 경로를 줄이는 도구이며 무조건 성능 해결책은 아니다.

11. 프레임워크를 넘어: React·Vue 공통 원리

11-1. 둘 다 결국 상태 변화 → 화면 동기화

React는 렌더 함수를 다시 평가하고 필요한 커밋을 수행한다. Vue는 반응형 의존성 추적과 업데이트 스케줄링을 활용한다. 구현 모델은 다르지만 목표는 상태와 UI를 일관되게 유지하는 것이다.

질문 React 관점 Vue 관점
상태 선언 useState, reducer 등 ref, reactive 등
파생 값 렌더 내 계산, useMemo computed
외부 동기화 useEffect watch, lifecycle hooks
항목 정체성 key :key
두 값의 연결 props + callback props + emits / v-model

11-2. 폼 상태 설계

제어 입력(controlled)은 상태가 입력 값을 관리한다. 비제어 입력(uncontrolled)은 DOM이 현재 입력 값을 갖는다. 100개의 입력 필드를 모두 매 키 입력마다 상위 컴포넌트 전체 렌더하게 하면 체감 지연이 커질 수 있다. 상태를 적절히 쪼개고, 필요한 부분만 업데이트한다.

11-3. 데이터 패칭 상태 머신

최소 상태: idle → loading → success | error. 실제 앱에는 refreshing, stale, empty가 추가될 수 있다. 상태를 추가할 때는 허용 전이를 명확하게 한다.

11-4. 브라우저와 서버의 책임 경계

  • 프론트: 입력 즉시 피드백, 접근성, 화면 상태.

12-2. LCP 개선

  • 큰 히어로 이미지를 적절한 크기·포맷으로 제공하고 width/height로 공간 예약.
  • 처음 필요한 리소스의 우선순위를 높이고, 필요 없는 렌더 차단 리소스를 줄인다.
  • 폰트 로딩, 서버 응답 지연(TTFB), CSR 기반 콘텐츠 늦은 표시를 분리한다.
  • 중요한 LCP 이미지를 무조건 lazy-load하지 않는다.

12-3. INP 개선

  • 메인 스레드의 긴 JS 작업을 쪼갠다.
  • 입력 핸들러에서 계산량 많은 정렬·필터를 반복하지 않는다.
  • DOM 레이아웃 읽기/쓰기를 분리한다.
  • 매우 큰 표나 리스트는 가상화·부분 렌더링 검토.
  • Web Worker는 CPU 처리 일부를 옮길 수 있지만 DOM에 직접 접근하지 못한다.

12-4. CLS 개선

  • 이미지/동영상/광고 영역에 크기 예약.
  • 위쪽에 콘텐츠를 갑자기 삽입하지 않음.
  • 웹 폰트 대체와 본문 길이 변화 고려.
  • 애니메이션은 가능한 레이아웃 변화가 적은 속성으로.

13. 프론트엔드 보안: 사고가 나는 경계

13-1. XSS: 문자열이 코드가 되는 순간

이 예제에서 textContent는 텍스트 노드 출력 맥락에 적절하다. URL, HTML 속성, CSS, JS 문자열 등 출력 위치마다 안전한 처리가 다르다. 사용자가 입력한 HTML을 허용해야 한다면 검증된 sanitizer와 정책이 필요하다.

13-2. CSP는 추가 방어선

Content Security Policy는 허용된 스크립트·이미지 등 출처와 실행 방식을 제한한다. 인라인 스크립트를 제한하는 nonce/hash 기반 정책이 효과적일 수 있지만, CSP만으로 XSS가 사라지는 것은 아니다.

13-3. CSRF와 XSS 차이

  • XSS: 공격자가 페이지 출처에서 악성 코드를 실행시키는 문제.
  • CSRF: 피해 브라우저가 지닌 인증 상태를 악용해 의도치 않은 요청을 보내게 하는 문제.
  • SameSite 쿠키, CSRF 토큰, Origin 검증 등의 방어는 시스템 설계에 맞춰 결합한다.

13-4. 권한 검증·민감 정보

프론트 라우터 가드와 버튼 숨김은 UX이며 서버 권한 확인의 대체가 아니다. API는 자원 소유권과 역할을 재검증해야 한다. 콘솔 로그·에러 추적 도구로 토큰/개인정보가 유출되지 않도록 로깅 정책을 만든다.

13-5. 보안 코드 리뷰 체크

  • innerHTML, dangerouslySetInnerHTML, eval, URL 쿼리 사용 지점 검색.
  • 링크·redirect URL의 프로토콜/허용 도메인 검증.
  • 외부 패키지와 스크립트 의존성 검토.
  • 비밀키를 프론트 빌드 환경변수에 넣지 않는다: 브라우저 코드에 포함되면 비밀이 아니다.
  • 쿠키·CORS·CSP·보안 헤더·오류 메시지 경계를 확인.

16. 모션그래픽 심화: 프레임·합성·Canvas·3D

이 장의 목표: 단순히 움직이는 UI를 만드는 것이 아니라, 모션의 수학적 모델 → 타이밍 → 브라우저 렌더링 단계 → GPU 작업 → 측정·접근성까지 설계할 수 있게 된다. 이 장은 01장(브라우저 렌더링)과 12장(성능)을 실제 애니메이션 구현에 연결한다.

16-1. 모션그래픽은 렌더링 절차의 '어느 한 단계'가 아니다

모션은 시간에 따라 시각 상태가 바뀌는 현상이다. x(t)(위치), opacity(t)(투명도), rotation(t)(각도), camera(t)(카메라 위치) 같은 값을 특정 시각에 평가해 연속된 프레임으로 보여준다. 애니메이션 값을 계산하는 주체와 그 결과를 픽셀로 출력하는 주체는 다를 수 있다.

  • 위의 세 경로는 대표적인 개념도다. 브라우저별 내부 구현, 레이어 상태, 해당 속성 및 주변 요소에 따라 달라진다.
  • transform·opacity를 적절한 합성 레이어에서 처리할 수 있으면 Layout/Paint 없이 컴포지터 중심으로 갱신할 수 있다. 항상 그렇게 되는 것은 아니다.
  • Canvas 2D는 애플리케이션이 픽셀 콘텐츠를 반복 갱신하며, WebGL·WebGPU는 주로 GPU가 그래픽스 파이프라인으로 장면을 그린다. 최종 출력은 브라우저 화면 합성에 참여한다.
  • CSS 애니메이션이나 Web Animations API 일부는 메인 스레드가 바빠도 컴포지터에서 계속 진행될 수 있다. 반대로 JS requestAnimationFrame의 계산은 보통 메인 스레드 작업이어서 긴 JS 태스크에 막힐 수 있다.

면접용 한 문장: “모션은 각 프레임의 상태를 갱신하는 과정이고, 변경한 속성과 실행 방식에 따라 Layout·Paint·Composite 중 필요한 단계가 달라집니다.”

16-2. 60Hz·120Hz와 프레임 예산: FPS만 보면 안 되는 이유

화면 주사율 전체 프레임 간격 의미
60Hz 약 16.67ms JS·스타일·레이아웃·페인트·합성·다른 작업까지 포함된 프레임 시간
90Hz 약 11.11ms 같은 코드라도 여유가 더 적음
120Hz 약 8.33ms 60fps만 가정한 고정 픽셀 이동은 속도가 달라짐
144Hz 약 6.94ms 타임스탬프 기반 모션이 필수

이 값은 애플리케이션 JS가 혼자 쓸 수 있는 시간이 아니라 전체 프레임 간격이다. 브라우저가 해야 할 다른 작업과 스케줄링까지 고려하면 실제 가용 시간은 더 짧다. 프레임을 놓치면 화면이 제때 갱신되지 않아 끊겨 보일 수 있다.

  • FPS(Frame Per Second): 단위 시간에 표시된 프레임의 수. 평균 FPS만으로는 순간적인 끊김을 드러내기 어렵다.
  • Frame time: 프레임 사이 간격과 프레임 처리를 위해 소비한 작업 시간을 구분해서 본다. 변동 폭이 심하면 움직임이 불규칙하다.
  • Long task / INP: 무거운 메인 스레드 작업은 입력 응답과 JS 애니메이션을 함께 지연시킬 수 있다.
  • Battery/GPU memory: 레이어를 많이 만들거나 고해상도 Canvas를 계속 다시 그리는 것은 다른 비용을 발생시킨다.

16-3. CSS Transition과 Keyframes: 상태 변화 vs 타임라인

transition은 시작 상태와 종료 상태 사이의 변화, @keyframes는 여러 시점으로 구성된 타임라인이다.

  • ease-in, ease-out, cubic-bezier()는 시간 → 진행률의 매핑을 바꾼다. 물리적인 질량이나 마찰을 실제로 시뮬레이션하는 것은 아니다.
  • steps()는 픽셀아트 프레임이나 스프라이트 이미지에 적합하다. 연속 보간이 아니라 불연속 단계를 만든다.
  • animation-fill-mode: both는 지연 시간과 종료 이후에도 키프레임 스타일을 반영할 수 있다. CSS 최종 기본 상태도 따로 설계하는 것이 좋다.
  • 시각적으로 감춘 요소의 키보드 포커스·접근성·클릭 가능 상태는 CSS opacity 하나로 해결되지 않는다. 비활성 요소는 hidden·inert·포커스 관리 등을 상황에 맞게 선택한다.

16-5. requestAnimationFrame: 시간에 따라 움직이기

requestAnimationFrame(callback)은 다음 화면 갱신 기회 이전에 콜백 실행을 요청한다. 콜백의 timestamp를 사용해야 60Hz와 120Hz에서 비슷한 속도를 유지할 수 있다. 탭이 가려지면 호출이 일시 중단되거나 크게 늦어질 수 있다.

실전 주의:

  • x += 2처럼 콜백당 고정 이동량을 더하면 화면 주사율에 따라 속도가 달라진다.
  • 게임 물리 계산은 deltaTime = timestamp - previousTimestamp와 속도(px/s)를 사용하고, 탭 복귀 시 deltaTime 상한을 두거나 고정 시뮬레이션 스텝을 고려한다.
  • 애니메이션은 스스로 requestAnimationFrame을 다시 호출할 때 계속된다. 언마운트, 화면 숨김, 정지 시 취소해야 한다.
  • requestAnimationFrame은 “렌더링 끝난 직후”가 아니라 다음 그리기 전 콜백이라는 점에 주의한다. 스타일 변경 뒤 레이아웃 값을 읽으면 강제 동기 레이아웃이 발생할 수 있다.

16-6. Web Animations API: DOM 애니메이션의 JS 제어

Web Animations API(WAAPI)는 CSS keyframes와 비슷한 애니메이션을 JS로 시작·중지·역재생·취소할 수 있다. 적합한 속성과 조건에서는 브라우저가 효과적으로 최적화할 수 있다.

  • fill: 'both'는 애니메이션의 효과가 끝난 뒤에도 시각 상태에 영향을 줄 수 있다. 영구적인 UI 상태는 가능하면 컴포넌트 스타일이나 클래스에 확정해서 관리한다.
  • animation.finished는 완료 시 해결되는 Promise이며 cancel() 시 거부될 수 있다. 비동기 대기 시 취소 상황까지 다룬다.
  • CSS 애니메이션과 WAAPI는 같은 렌더링 시스템을 활용할 수 있다. WAAPI라서 항상 더 빠른 것은 아니다.

16-7. FLIP: 레이아웃은 바뀌었지만 이동은 transform으로

First → Last → Invert → Play. 목록 정렬이나 드래그 앤 드롭처럼 목표 위치가 레이아웃에 의해 결정되는 경우 유용한 패턴이다.

한계: getBoundingClientRect()는 레이아웃 값을 읽는 작업이다. 스타일 변경 직후 읽으면 강제 레이아웃이 발생할 수 있다. FLIP은 필요한 위치 측정을 묶고, 이후 반복 프레임에는 transform을 사용해서 비용을 줄이는 전략이다. 기존 transform, 중첩 스크롤, position: fixed, 재정렬 도중 중복 애니메이션, 포커스 이동도 고려해야 한다.

16-8. will-change, 레이어 승격, GPU 가속의 오해

  • 레이어 승격(layer promotion)은 특정 콘텐츠를 독립적으로 합성할 수 있도록 관리하는 최적화다. 브라우저가 레이어를 만드는 조건은 복잡하며 구현에 따라 달라진다.
  • will-change는 브라우저에 변경 가능성을 힌트로 주는 것일 뿐 GPU 가속을 강제하는 스위치가 아니다. 너무 많은 레이어는 메모리·래스터화·컴포지팅 비용을 높인다.
  • transform: translateZ(0)을 무조건 붙이는 관행은 피한다. 실제 성능과 텍스트 렌더링·레이어 상태가 달라질 수 있다.
  • transform이 요소에 적용되면 stacking context와 기준 블록 등 레이아웃 관계에 영향을 줄 수 있다. 화면이 부드러워도 z-index·fixed 동작이 바뀔 수 있다.
  • GPU에서 합성된다고 모든 애니메이션이 공짜는 아니다. 거대한 반투명 레이어, 필터, 그림자, 블러, 고DPR 화면의 픽셀 작업은 여전히 무거울 수 있다.

Q1. 모션그래픽은 브라우저 렌더링의 어느 단계에서 발생하나요?

Q3. requestAnimationFrame은 setInterval과 어떻게 다른가요?

01. 브라우저가 HTML을 렌더링하는 큰 흐름은?

핵심 답변 Navigation/HTTP → HTML 파싱(DOM), CSS 파싱(CSSOM) → 스타일 계산 및 렌더링에 필요한 시각 구조 구성 → Layout(크기·위치) → Paint(그리기 명령) → Rasterization(픽셀화) → Composite(합성). 실제 다운로드·파싱은 겹치며, 화면 업데이트에서는 속성별로 일부 단계만 재실행될 수 있다.

왜 그런가 · 심화 DOM은 문서 구조, CSSOM은 스타일 규칙을 다룬다. 스타일 계산·레이아웃·페인트는 변경된 부분을 중심으로 필요할 때 다시 수행된다. 이것은 개념적인 흐름이며 엔진별 내부 구현과 병렬 처리에는 차이가 있다.

실전 적용 예

02. async와 defer 차이는?

왜 그런가 · 심화 둘 다 다운로드는 HTML 파싱과 겹칠 수 있다. 고전 외부 defer 스크립트는 문서 순서를 지키고 DOMContentLoaded 전에 실행되지만, async는 다운로드 완료 시점에 따라 실행 순서가 바뀐다. 일반 모듈 스크립트는 기본적으로 지연 실행 특성을 가진다.

03. DOMContentLoaded와 load의 차이는?

핵심 답변 전자는 HTML 파싱 및 지연 스크립트 실행 완료 중심, 후자는 이미지 등 의존 리소스 완료를 포함.

04. Layout과 Paint의 차이는?

핵심 답변 Layout은 크기/위치 계산, Paint는 시각 내용 그리기 명령 생성. 변경 속성에 따라 비용 다름.

왜 그런가 · 심화 Layout은 박스의 기하 정보와 배치를 산정하고 Paint는 텍스트·배경·테두리 등 그릴 작업을 만든다. 래스터화와 합성은 이후 픽셀·레이어를 화면에 표시하는 단계다. 위치나 크기를 바꾸면 Layout부터, 단순 색을 바꾸면 Paint부터 다시 필요할 수 있다.

05. 버튼을 div로 대체하면 왜 문제인가?
