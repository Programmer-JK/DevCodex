0-1. 먼저 JDK·JRE·JVM 차이를 확실히 이해

JDK는 개발 도구 세트로서 javac 컴파일러와 java 실행 도구를 포함한다. JVM은 바이트코드를 실행하며 메모리·스레드·GC를 관리한다. JRE는 역사적으로 실행 환경을 가리키는 용어이며, 최신 JDK 배포판에서는 별도 JRE 설치를 전제로 개발하지 않는다. Spring Boot를 만들려면 컴파일이 필요하므로 JDK를 설치해야 한다.

Hello.java / Java의 컴파일·실행 단계java
// Hello.java
public class Hello {
    public static void main(String[] args) {
        System.out.println("JDK → javac → bytecode → JVM 실행");
    }
}

// 터미널:
// javac Hello.java   → Hello.class (bytecode)
// java Hello         → JVM이 Hello.main() 실행

1. Spring은 어떤 문제를 해결하려고 등장했을까?

개발 초기에는 객체가 몇 개 없어서 new로 직접 만들고 사용해도 별문제가 없어 보인다. 그런데 기능이 커지면 주문 서비스는 결제 서비스, 재고 서비스, 알림 서비스에 의존하고, 이들이 다시 DB·외부 API·설정에 의존한다. 객체를 만드는 위치가 여기저기 흩어지면 구현체 교체, 테스트, 설정 관리가 어려워진다.

예를 들어 결제 기능이 KakaoPaymentClient를 직접 생성한다면 테스트 중에도 실제 결제 API 연결 가능성이 생긴다. 테스트에서는 가짜 결제 객체를 넣고 싶고, 운영에서는 진짜 구현을 넣고 싶다. 그때 중요한 건 결제 서비스가 구체적으로 어떤 객체가 만들어지는지 몰라도 자신의 일을 수행할 수 있게 만드는 것이다.

IoC와 DI를 헷갈리지 않는 방법

IoC(Inversion of Control)는 제어의 주도권을 외부로 옮긴다는 원칙이다. DI(Dependency Injection)는 그중 객체가 사용할 의존 대상을 밖에서 전달받는 구체적인 방식이다. Spring은 컨테이너가 객체를 만들고 조립하는 방식으로 IoC를 구현한다.

Bean은 Spring 컨테이너가 관리하는 객체다. new Member()로 직접 만든 객체는 자동으로 Bean이 되지 않는다. Spring에 등록된 구성정보에 따라 만들어지거나 전달되어야 컨테이너의 관리 대상이 된다.

간단한 Spring 예시

public interface MessageSender {
    void send(String message);
}

@Component
public class EmailSender implements MessageSender {
    public void send(String message) {
        // 외부 메일 전송 구현
    }
}

@Service
public class NotificationService {
    private final MessageSender sender;

    public NotificationService(MessageSender sender) {
        this.sender = sender;
    }

    public void notifyUser(String message) {
        sender.send(message);
    }
}

위 코드에서 NotificationService는 EmailSender를 생성하지 않는다. 필요한 역할인 MessageSender만 선언한다. 컨테이너는 등록된 구현 Bean을 찾아 생성자에 전달한다. 단, MessageSender 구현체가 여러 개라면 후보를 결정하도록 @Qualifier, @Primary 등을 고려해야 한다.

면접에서 한 단계 더: “DI 덕분에 테스트가 쉽습니다”에서 끝내지 말자. “예를 들어 알림 서비스는 SMTP 연결을 모르고 MessageSender 계약에만 의존하므로 테스트에서 메모리 기반 대역을 주입해 발송 여부를 검증할 수 있습니다”라고 말하면 구조를 이해했다는 인상을 준다.

직접 해볼 것: 위 예시에서 MessageSender 구현을 하나 더 만들면 애플리케이션 시작 시 어떤 일이 생기는지 예상하고 실행해 보자. 순수 Java DI Mission 01의 정답 코드는 여기서 제공하지 않는다.

2. Spring Boot 실행 버튼을 누르면 실제로 무슨 일이 일어날까?

SpringApplication.run(...)을 호출하면 Spring Boot는 환경설정과 애플리케이션 유형을 해석하고 적절한 ApplicationContext를 준비한 뒤 Bean 정의를 등록·구성하고 컨텍스트를 갱신한다. 이 과정에서 컴포넌트 스캔, 자동 설정, Bean 생성·주입, 초기화 등이 이루어진다. 웹 애플리케이션이라면 조건에 따라 내장 서버가 준비·시작된다.

대략적인 흐름:

  1. main()이 시작되고 Boot가 환경 정보와 설정을 준비한다.
  2. @SpringBootApplication을 기준으로 컴포넌트 스캔과 자동 설정 구성이 결정된다.
  3. 설정 조건에 맞는 Bean 정의가 컨테이너에 등록된다.
  4. 컨테이너가 필요한 Bean을 만들고 의존성을 주입한다.
  5. Bean 초기화 과정과 컨텍스트 갱신을 거쳐 애플리케이션이 준비된다.
  6. 웹 앱이라면 내장 Servlet 서버가 HTTP 요청을 받을 수 있는 상태가 된다.

이건 개념을 이해하기 위한 축약된 흐름이다. 실제 순서에는 BeanFactory 후처리, BeanPostProcessor, 라이프사이클 처리와 여러 이벤트가 끼어든다.

자동 설정은 마법이 아니라 조건식이다

예를 들어 JDBC 관련 의존성이 있고 DataSource 설정을 제공하면 Boot가 DataSource 관련 구성을 해줄 수 있다. 하지만 사용자가 직접 DataSource Bean을 정의했다면 조건에 따라 자동 구성이 물러날 수 있다. 그래서 왜 특정 Bean이 만들어졌는지 살피려면 조건 평가 보고서를 확인해야 한다.

@SpringBootApplication의 세 축을 기억하자.

  • @SpringBootConfiguration: 설정 클래스 역할.
  • @EnableAutoConfiguration: 조건부 자동 설정 활성화.
  • @ComponentScan: 애플리케이션 패키지 기준 컴포넌트 탐색.

실행은 되는데 Bean을 찾지 못한다면?

실무에서 확인할 순서는 대략 다음과 같다.

  1. 찾는 객체가 실제 Spring Bean으로 등록되었는가?
  2. 스캔 대상 패키지 안에 있는가?
  3. Profile이나 조건부 구성으로 제외되지 않았는가?
  4. 동일 타입 Bean이 여러 개여서 선택이 모호한가?
  5. 순환 의존이 있는가?

비슷하게 생긴 두 오류: NoSuchBeanDefinitionException은 후보를 찾지 못하는 쪽이고, NoUniqueBeanDefinitionException은 후보가 너무 많아 결정할 수 없는 쪽이다.

3. Bean은 언제 만들어지고, 여러 사람이 동시에 쓰면 어떻게 될까?

Spring Bean의 기본 Scope는 singleton이다. 여기서 singleton은 하나의 Spring 컨테이너와 해당 Bean 정의를 기준으로 인스턴스를 재사용한다는 의미다. 일반적인 웹 서버에서 여러 요청 스레드가 같은 Service Bean 인스턴스를 호출할 수 있다.

이때 아래 코드는 위험하다.

@Service
public class DangerousService {
    private String currentUserId; // 요청마다 바뀌는 공유 상태!

    public void process(String userId) {
        currentUserId = userId;
        // 다른 요청 스레드가 currentUserId를 바꿀 수 있다.
    }
}

한 사용자의 요청을 처리하는 사이 다른 요청이 currentUserId를 덮어쓸 수 있기 때문이다. 대신 요청에 필요한 데이터는 메서드 인자나 요청 스코프 등 적절한 위치에서 전달하고, 공유 Bean은 가능하면 상태 없는 구조로 만든다.

Bean의 생명주기

컨테이너는 등록된 Bean 정의를 바탕으로 객체를 생성하고, 의존성을 채운 뒤, 초기화 콜백을 실행한다. 컨테이너가 종료될 때는 관리되는 Bean의 종료 콜백을 호출할 수 있다. @PostConstruct는 초기화 시점, @PreDestroy는 적절한 종료 시점에 사용한다. 다만 prototype Bean은 생성 후의 전체 생명주기까지 Spring이 자동으로 관리하지 않는다는 점에 주의하자.

질문: @PostConstruct 안에서 같은 클래스의 @Transactional 메서드를 호출하면 어떻게 될까?
해설: 트랜잭션 프록시가 완전히 적용되기 전의 초기화 코드에 이를 의존하지 말아야 한다. 초기화 완료 시점과 프록시의 경계를 이해하는 것이 핵심이다.

4. AOP와 프록시는 왜 중요한가?

비즈니스 메서드마다 beginTransaction()/commit()/rollback()을 작성하면 중복이 커지고 누락이 생긴다. Spring은 트랜잭션 같은 공통 기능을 실제 비즈니스 메서드 호출을 둘러싸는 프록시에서 처리할 수 있다.

Controller
    │
    ▼
OrderService Proxy ── 트랜잭션 시작
    │
    ▼
진짜 OrderService.pay() ── 비즈니스 로직과 DB 접근
    │
    ▼
OrderService Proxy ── 정상: 커밋 / 롤백 조건: 롤백

이 구조를 알아야 Spring 면접의 단골 함정인 자기 호출(self-invocation)을 이해할 수 있다.

@Service
public class OrderService {
    public void process() {
        saveOrder(); // 같은 객체 내부에서 직접 호출
    }

    @Transactional
    public void saveOrder() {
        // DB 저장
    }
}

외부에서 process()를 호출하면, process() 내부의 saveOrder() 호출은 프록시를 다시 통과하지 않는다. saveOrder()에만 붙은 트랜잭션 경계는 이 내부 호출로 새롭게 적용되지 않는다. 단, 외부 호출이 이미 트랜잭션 안에 있었다면 그 기존 트랜잭션은 적용될 수 있다.

실무에서는 트랜잭션 경계가 필요한 동작을 별도 Service Bean으로 분리하거나, 공개 메서드를 외부에서 프록시를 통해 호출하도록 설계하는 편이 명확하다. 무작정 자기 자신을 주입받는 방법부터 선택하지 말자.

AOP 용어를 면접용으로 정리

용어 쉽게 풀어 말하면
Target 실제 일을 하는 대상 객체
Proxy 대상을 감싸서 호출을 가로채는 객체
Advice 호출 전후로 실행하는 부가 로직

Join point 부가 로직이 적용 가능한 실행 지점. Spring AOP는 주로 메서드 실행에 초점

5. 사용자가 API를 호출했을 때 내부를 따라가 보자

예시 상황은 GET /api/members/42다. 프론트엔드에서 회원 상세를 요청하고, Spring MVC가 이를 JSON으로 반환한다고 가정한다.

Browser/Next.js
   │  GET /api/members/42
   ▼
Servlet Filter Chain (보안, 요청 전처리)
   │
   ▼
DispatcherServlet
   │
   ├─ HandlerMapping: 어떤 컨트롤러 메서드인가?
   └─ HandlerAdapter: 인자 바인딩 후 메서드 호출
          │
          ▼
      MemberController
          │
          ▼
      MemberService
          │
          ▼
      Repository/Mapper ── SQL ── Database
          │
          ▼
      DTO → HttpMessageConverter → JSON 응답
@RestController
@RequestMapping("/api/members")
public class MemberController {
    private final MemberService memberService;

    public MemberController(MemberService memberService) {
        this.memberService = memberService;
    }

    @GetMapping("/{id}")
    public ResponseEntity<MemberResponse> find(@PathVariable Long id) {
        MemberResponse response = memberService.findMember(id);
        return ResponseEntity.ok(response);
    }
}

@RestController가 문자열을 반환하면 왜 View 이름으로 보지 않을까?

@RestController는 @ResponseBody의 의미를 포함하기 때문에 반환값이 HTTP 응답 본문으로 처리된다. JSON 응답이라면 적절한 HttpMessageConverter가 Java 객체를 직렬화한다. 반면 일반 @Controller가 View 이름을 반환한다면 ViewResolver가 화면 렌더링에 관여할 수 있다.

검증은 어느 계층에서 해야 할까?

요청 형식과 기본 제약(필수값, 길이, 포맷)은 Controller 경계에서 DTO와 Bean Validation으로 확인하기 좋다. “해당 계정은 이 주문을 취소할 권한이 있는가”처럼 DB 상태를 고려하는 규칙은 Service/도메인 계층에서 확인해야 한다. HTTP 요청 검증과 업무 규칙 검증은 목적이 다르다.

public record CreateMemberRequest(
    @NotBlank String name,
    @Email String email
) {}

@PostMapping
public ResponseEntity<Void> create(@Valid @RequestBody CreateMemberRequest request) {
    // 요청 형식 검증 이후 서비스에 전달
    return ResponseEntity.status(201).build();
}

위 예시는 구조 이해용이며 import와 서비스 구현은 생략했다. @Valid를 쓰려면 Bean Validation 관련 의존성과 구성이 필요하다.

예외를 공통 처리하는 이유

컨트롤러마다 예외를 제각각 잡아 200 OK와 오류 문자열을 반환하면 클라이언트가 실패를 판별하기 어렵다. @RestControllerAdvice에서 예외를 분류해 일관된 오류 본문과 상태 코드를 제공할 수 있다. 예를 들어 입력 오류는 400, 권한 거부는 403, 존재하지 않는 리소스는 404 등 정책을 정한다. 단, 모든 예외를 500으로 뭉개지 말고 예상 가능한 업무 오류와 시스템 오류를 구분한다.

6. 트랜잭션은 단순히 ’롤백해 주는 어노테이션’이 아니다

주문 생성은 주문 행 저장, 재고 차감, 결제 상태 변경이 함께 움직여야 할 수 있다. 이 작업을 각각 독립 커밋하면 중간 실패 때 데이터가 어긋날 위험이 있다. 따라서 업무적으로 함께 성공하거나 함께 실패해야 하는 범위를 트랜잭션 경계로 잡는다.

@Service
public class OrderApplicationService {
    @Transactional
    public void placeOrder(OrderCommand command) {
        orderRepository.save(command.toOrder());
        stockRepository.decrease(command.productId(), command.quantity());
        // 실제 결제 API 호출은 트랜잭션 경계·실패 복구 전략을 따로 검토
    }
}

어떤 예외가 발생하면 롤백할까?

기본 동작은 RuntimeException과 Error가 롤백 대상이다. Checked Exception은 기본적으로 그렇지 않다. 직접 rollbackFor = Exception.class를 명시하는 등 정책을 바꿀 수 있다. Spring Framework 6.2 이상에는 전역 기본 롤백 규칙을 변경하는 설정도 있으므로 실제 프로젝트 설정을 확인하자.

@Transactional(rollbackFor = Exception.class)
public void importData() throws IOException {
    // IOException도 롤백하도록 명시
}

예외를 잡으면 어떻게 될까?

@Transactional
public void importData() {
    try {
        repository.save(...);
        doSomethingRisky();
    } catch (RuntimeException ex) {
        log.warn("실패했지만 메서드는 정상 종료", ex);
    }
}

프록시는 이 메서드가 정상 반환된 것으로 볼 수 있기 때문에 자동 롤백되지 않을 수 있다. 단, 하위 트랜잭션 참여자가 이미 rollback-only로 표시했거나 DB가 오류 상태에 들어간 경우에는 최종 결과가 달라질 수 있다. 이 함정을 ’무조건 커밋’으로 외우면 안 된다.

Propagation을 실제 상황으로 이해

REQUIRED는 현재 트랜잭션에 참여하고 없으면 만든다. 일반적인 업무 메서드에 적합하다. REQUIRES_NEW는 바깥 트랜잭션과 독립된 트랜잭션을 실행한다. 예를 들어 주문 실패와 무관하게 실패 이력을 남겨야 하는 로그 저장에는 독립 트랜잭션을 검토할 수 있다. 그러나 실행 중 추가 DB 연결이 필요할 수 있고, 내부 호출로 프록시를 우회하면 기대한 결과가 나오지 않는다.

격리 수준은 왜 필요한가?

두 사용자가 동시에 동일 재고 1개를 구매한다고 가정해 보자. 둘 다 재고를 1로 조회한 뒤 각각 1을 차감하면 논리적으로 재고가 음수여야 하는 상황이 놓칠 수 있다. 이때 단순히 @Transactional을 붙이는 것만으로 모든 동시성 문제가 해결되는 것은 아니다. 적절한 조건부 갱신 SQL, 낙관적/비관적 락, 고립 수준, 재시도 전략을 함께 설계해야 한다.

실무 판단 기준: 트랜잭션은 짧게 유지하고, 네트워크 호출이나 긴 파일 처리와 DB 락을 한 경계에 묶기 전에 실패 복구 방법을 설계한다.

7. MyBatis와 JPA는 어떻게 다른 사고방식을 요구할까?

MyBatis: SQL을 중심으로 명시적으로 제어

MyBatis에서는 SQL을 직접 작성하고 결과를 객체에 매핑한다. 복잡한 조회, 레거시 테이블, 특정 DB 기능을 명시적으로 사용해야 하는 환경에 유리하다.

@Mapper
public interface MemberMapper {
    @Select("SELECT ID, NAME FROM MEMBER WHERE ID = #{id}")
    MemberRow findById(long id);
}

매퍼와 SQL을 직접 제어하기 때문에 실행되는 쿼리가 비교적 명확하다. 그 대신 SQL 변경과 결과 매핑을 개발자가 관리해야 하며, 많은 반복 CRUD를 작성해야 할 수 있다.

JPA: 영속성 컨텍스트가 객체 상태를 관리

JPA는 ORM 명세이고 Hibernate는 대표적인 구현체다. EntityManager가 영속 객체를 관리하며, 영속 상태의 Entity 필드가 변경되면 Flush 시점에 변경 SQL을 생성할 수 있다.

@Transactional
public void renameMember(Long id, String name) {
    Member member = entityManager.find(Member.class, id);
    member.changeName(name);
    // 영속 객체라면 Dirty Checking으로 UPDATE가 반영될 수 있다.
}

그렇다고 이 메서드가 실행될 때마다 무조건 UPDATE가 발생하는 것은 아니다. 실제 상태 변경 여부, Flush 시점, Provider 동작을 봐야 한다.

Flush와 Commit을 분리해서 생각하자

  • flush(): 메모리의 영속성 컨텍스트 변경을 DB SQL로 동기화한다.
  • commit(): 트랜잭션을 최종 확정한다.
  • Flush 후에도 트랜잭션이 롤백되면 일반적으로 데이터 변경은 확정되지 않는다.

N+1은 왜 생길까?

주문 100건을 조회할 때 주문 목록을 가져오는 SQL 1회 뒤, 주문마다 회원 정보를 조회하는 SQL이 추가된다면 최대 101회 쿼리가 나갈 수 있다. API 응답 시간이 갑자기 길어져도 코드만 보면 반복문 하나로 보일 수 있다.

진단 단계: SQL 로그/쿼리 카운트 확인 → 어떤 연관 접근이 추가 조회를 유발하는지 찾기 → 필요한 데이터의 조회 범위 결정 → Fetch Join·EntityGraph·배치 페치·DTO Projection 중 선택 → 실제 쿼리 수 재측정.

Spring 면접에서는: “JPA가 무조건 MyBatis보다 좋다”가 아니라, 조회 SQL을 통제해야 하는 환경과 도메인 변경을 객체 중심으로 다루는 환경의 차이를 이야기하는 편이 더 설득력 있다.

8. Spring Security의 요청 흐름을 한 번에 이해하자

인증은 누구인가, 인가는 무엇을 할 수 있는가다. 예를 들어 로그인한 일반 직원이라고 해서 타 직원의 급여를 열람할 수 있는 것은 아니다. 인증이 성공한 다음에도 요청 대상 데이터에 대한 권한을 검사해야 한다.

HTTP 요청
   ↓
Servlet FilterChain
   ↓
Spring Security FilterChainProxy
   ├─ 인증 처리: 세션 / Bearer Token 검증 등
   ├─ SecurityContext에 Authentication 제공
   └─ 인가 검사: URL·메서드·업무 리소스 정책
   ↓
DispatcherServlet → Controller → Service

JWT를 쓸 때 꼭 답할 질문

  1. 토큰 서명이 유효한가? 만료되었는가?
  2. 토큰을 어떤 위치에서 받는가? (Authorization 헤더/쿠키 등)
  3. 접근 토큰을 탈취하면 어떻게 대응하는가?
  4. Refresh Token은 어떻게 저장·회전·폐기하는가?
  5. 단순 역할뿐 아니라 리소스 소유권을 검증하는가?

JWT는 클라이언트가 신원을 증명하기 위한 토큰 형식 중 하나지, 그 자체가 권한 정책의 완성은 아니다.

CORS와 CSRF를 따로 보는 이유

CORS는 브라우저가 다른 출처의 응답을 JavaScript에서 읽을 수 있는지 제어하는 정책이다. API 서버로 요청이 전혀 들어오지 못하게 하는 보안 장벽과 동일시하면 안 된다. CSRF는 브라우저가 자동으로 첨부하는 인증 정보(예: 쿠키)를 악용하여 사용자가 의도하지 않은 작업을 하게 하는 공격이다. 그래서 서로 다른 문제다.

종권의 Runique 경험 연결: JWT·Spring Security 구현을 설명할 때 단순히 “로그인 붙였습니다”에서 끝내지 말고, 필터에서 어떤 인증을 처리하고 Service에서 어떤 권한을 검증했는지 구분해 답해 보자. 실제 구현하지 않은 동작은 구현했다고 말하지 않는다.

9. Java 메모리와 대용량 처리 — 실무 경험을 이론으로 정리

Java 개발자가 GC를 아는 이유는 “메모리는 자동 관리된다”를 말하기 위해서가 아니다. 메모리가 언제, 얼마나, 어떤 객체에 의해 점유되는지 추적하기 위해서다.

객체가 크면 무엇이 문제일까?

문서 하나에 HTML 문자열, Base64 이미지 문자열, 디코딩한 이미지 바이트 배열, 리사이징 중간 버퍼, DB LOB용 버퍼가 동시에 존재하면 원본 파일 크기보다 훨씬 큰 일시적 메모리 사용량이 발생할 수 있다. Base64 자체도 바이너리 데이터 대비 크기가 증가한다.

진단 순서:

  1. 어떤 처리 단계에서 메모리 사용량이 급증하는지 측정한다.
  2. 한 번에 읽는 데이터 크기와 동시 처리 건수를 확인한다.
  3. 대형 객체가 얼마나 오래 살아 있는지와 참조 해제 가능 시점을 살핀다.
  4. 스트리밍·청크·단건 처리·이미지 리사이징 등으로 메모리 사용량을 제한한다.
  5. DB 측 임시 LOB, 세션, 커넥션 등 Java GC 밖 자원의 수명도 점검한다.

실무 답변 예시 구조: “우리은행 마이그레이션에서 레코드당 큰 이미지 데이터를 한꺼번에 처리하면서 메모리 부담이 생겼습니다. 이미지 크기를 줄이고 처리 단위를 분리했으며, Oracle 임시 LOB도 명시적으로 해제하도록 바꾸었습니다. 단순히 힙 크기만 늘리는 방식으로 접근하지 않았습니다.” — 본인이 실제로 한 조치만 말하자.

10. DB 성능이 느릴 때는 무엇부터 확인할까?

Spring 앱의 느린 API가 항상 Java 코드 문제인 것은 아니다. 특히 금융권 시스템에서는 SQL, 인덱스, 락, DB 세션, 커넥션 풀이 병목일 수 있다.

순서가 중요한 이유

  1. 수치 확보: 어떤 API가 얼마나 느린지 P95 응답시간, 오류율, 부하를 측정한다.
  2. 구간 분리: Controller 진입부터 DB 호출 전후, 외부 API 구간별 시간을 잰다.
  3. SQL 확인: 실행 SQL, 바인딩 값 유형, 실행 계획, 처리 행 수, 인덱스·조인 순서를 본다.
  4. 대기 확인: DB 락, 풀 대기, Thread 대기, GC Stop-the-world 여부를 본다.
  5. 한 가지씩 변경: 인덱스 추가, 쿼리 수정, 호출 횟수 감소, 캐시 적용 등 가설을 검증한다.

인덱스 예시

WHERE CUSTOMER_ID = ? AND CREATED_AT >= ? ORDER BY CREATED_AT DESC와 같은 조회를 자주 한다면 CUSTOMER_ID, CREATED_AT을 포함하는 복합 인덱스를 검토할 수 있다. 하지만 실제 선택도, 통계, 데이터 분포, 다른 쿼리와 쓰기 비용을 함께 확인해야 한다. 실행 계획 없이 무조건 인덱스를 만들면 오히려 쓰기 성능만 나빠질 수 있다.

Connection Pool 고갈의 전형적인 징후

DB CPU는 높지 않은데 웹 요청이 오래 대기하고, 커넥션 획득 타임아웃이 발생한다면 풀 고갈을 의심할 수 있다. 느린 쿼리·외부 호출을 포함한 긴 트랜잭션·반환되지 않은 연결이 원인일 수 있다. 이때 풀 최대 크기만 늘리면 DB 병목이 커질 수도 있다.

11. 실무 테스트는 무엇을 어느 범위에서 검증할까?

테스트는 단순히 ’코드 커버리지 80%’를 만들기 위한 일이 아니다. 변경해도 깨지면 안 되는 계약을 검증하기 위한 안전장치다.

테스트 확인하는 것 예시
순수 단위 테스트 업무 규칙 자체 재고 수량 부족 시 주문 거부
MVC 슬라이스 테스트 URL, 바인딩, 응답 상태, JSON GET /members/42의 200/404
DB 통합 테스트 실제 SQL, 매핑, 제약, 트랜잭션 중복 키/롤백 동작
E2E 테스트 실제 사용자 여정 로그인 → 주문 → 조회

Spring Boot에서는 @SpringBootTest, @WebMvcTest, MockMvc 등으로 테스트 범위를 선택할 수 있다. 다만 Boot 4는 테스트 모듈 구성과 패키지 경로가 일부 달라졌으므로 사용 중인 버전의 문서를 확인하자.

테스트가 알려주는 설계 문제

업무 규칙 하나를 테스트하려고 매번 실제 DB와 메일 서버를 띄워야 한다면 객체 간 책임이 너무 강하게 묶여 있을 수 있다. 이때 생성자 DI와 역할 분리가 해결의 단서가 된다.

종권의 Oxid 경험 연결: Playwright E2E와 단위 테스트를 작성한 경험은 강점이다. 면접에서는 “어떤 오류가 단위 테스트에서 잡히고 어떤 오류는 E2E에서만 잡히는가”를 구체적으로 설명하면 실무 감각이 드러난다.

12. 경력직 면접에서는 어떻게 말해야 할까?

경력직 면접에서 정의만 정확하게 외워도 금방 깊이가 드러난다. 면접관이 확인하는 것은 다음 네 가지다.

  1. 정의: 무엇인가?
  2. 이유: 왜 사용하는가?
  3. 원리: 내부에서 어떻게 동작하는가?
  4. 실무: 언제 문제가 생겼고 어떻게 해결했는가?

예시 ① “DI를 왜 사용하나요?”

짧은 답: “객체가 필요한 구현체를 직접 생성하지 않고 외부에서 전달받게 하여 결합도를 낮추고 교체와 테스트를 쉽게 하기 위해서입니다.”
깊은 답: “예를 들어 주문 서비스가 결제 API 구현 클래스를 직접 new하면 운영 결제 API에 강하게 묶입니다. 역할 인터페이스를 의존하고 생성자로 주입하면 운영에서는 실제 구현을, 테스트에서는 대역을 넣을 수 있습니다. Spring은 컨테이너가 이 조립을 관리해 줍니다.”

예시 ② “@Transactional은 어떻게 동작하나요?”

짧은 답: “기본적으로 Spring AOP 프록시가 메서드 호출을 가로채 트랜잭션 매니저를 통해 시작, 커밋, 롤백을 처리합니다.”
깊은 답: “외부에서 프록시를 거쳐 호출되는 것이 중요합니다. 같은 객체 내부의 this.method() 호출은 프록시를 우회하므로 해당 메서드에 붙은 트랜잭션 설정이 새로 적용되지 않을 수 있습니다. 기본 롤백 대상도 RuntimeException과 Error라서 Checked Exception은 정책을 확인해야 합니다.”

예시 ③ “MyBatis와 JPA는 무엇이 다른가요?”

짧은 답: “MyBatis는 SQL과 결과 매핑을 직접 제어하는 접근이고, JPA는 객체의 영속 상태를 관리하는 ORM 명세입니다.”
깊은 답: “복잡한 Oracle SQL과 레거시 스키마를 다뤘던 업무에서는 명시적 SQL 제어가 중요했습니다. 반면 객체의 상태 변경이 중심인 도메인에서는 JPA의 영속성 컨텍스트와 변경 감지가 이점이 될 수 있습니다. JPA를 선택해도 N+1과 Flush 타이밍을 모르면 성능과 정합성 문제가 생길 수 있습니다.”

면접 전에 최종 점검

  • IoC와 DI를 구분해서 설명할 수 있는가?
  • @Transactional의 프록시와 예외 롤백 조건을 설명할 수 있는가?
  • HTTP 요청이 SecurityFilterChain, DispatcherServlet, Controller를 지나는 흐름을 그릴 수 있는가?
  • 3계층 분리 이유를 변경·테스트 관점에서 설명할 수 있는가?
  • MyBatis를 써 본 경험과 JPA를 공부한 내용을 사실대로 구분할 수 있는가?
  • 느린 SQL이나 메모리 문제를 측정 → 원인 → 조치 → 결과로 이야기할 수 있는가?

이 질문 중 하나라도 막히면 해당 장으로 돌아가 짧은 실험을 해보자. 강의를 끝까지 듣는 것보다 본인이 직접 만든 코드를 설명할 수 있게 되는 편이 훨씬 큰 변화다.

Part 1. Java 기초: Spring을 이해하기 위한 바닥

01. JDK, JRE, JVM ★

용어 뜻 기억할 점
JDK 개발 도구 묶음(컴파일러 등) 개발에 필요
JRE Java 애플리케이션 실행 환경 전통적으로 JVM과 실행 라이브러리 등을 뜻함
JVM 바이트코드를 실행하는 가상 머신 메모리 관리·GC·JIT 컴파일

실행 과정: .java → javac → .class 바이트코드 → JVM 실행(인터프리터/JIT). 현대 JDK 배포에서 JRE가 반드시 별도 설치물로 제공되는 것은 아니다.

면접 답변: “Java는 소스코드를 바이트코드로 컴파일한 뒤 JVM 위에서 실행합니다. JVM은 클래스 로딩, 실행, 메모리 관리와 GC를 담당합니다.”

02. 기본형과 참조형 ★

  • 기본형: int, long, boolean, double 등. 변수에 값을 직접 저장한다.
  • 참조형: 배열, String, 일반 객체 등. 변수에는 객체에 대한 참조값이 들어간다.
  • Java 메서드 인자는 항상 값으로 전달된다. 객체를 인자로 넘길 때도 참조값이 복사된다. 따라서 메서드에서 객체 상태를 변경할 수 있지만, 파라미터를 새 객체로 재할당해도 호출자 변수는 바뀌지 않는다.

03. Stack, Heap, GC ★★

  • Stack: 메서드 호출 프레임, 지역 변수 등을 관리한다(개념적 설명).
  • Heap: 객체와 배열이 주로 할당되는 영역이다.
  • GC: 더 이상 도달할 수 없는 객체의 메모리를 회수한다.
  • OutOfMemoryError는 단순히 “GC를 안 해서” 발생하는 것이 아니다. 대용량 객체, 메모리 누수, 메모리 한도, 오프힙/네이티브 자원 등 원인을 구분해야 한다.

실무 연결: 우리은행 마이그레이션의 100MB급 레코드·Base64 이미지 문제는 대용량 객체 생성량과 사용 기간을 줄이는 설계(이미지 축소, 단건 처리)가 중요했다는 사례로 설명할 수 있다.

04. == vs equals() vs hashCode() ★

  • ==: 기본형은 값 비교, 참조형은 참조의 동일성 비교.
  • equals(): 논리적 동등성 비교. 기본 구현은 동일성 비교이므로 필요 시 재정의.
  • hashCode(): 해시 기반 컬렉션의 버킷 판단에 쓰인다.
  • 규칙: equals()가 true인 두 객체는 반드시 같은 hashCode()를 반환해야 한다. 반대는 성립하지 않는다.
  • HashMap의 키는 넣은 뒤 동등성/해시값이 바뀌면 조회가 어려워질 수 있으므로 불변 키가 안전하다.

05. List, Set, Map ★

자료구조 목적 대표 구현
List 순서 있는 요소 모음, 중복 허용 ArrayList, LinkedList
Set 중복 없는 요소 집합 HashSet, TreeSet
Map 키-값 매핑, 키 중복 불가 HashMap, TreeMap, ConcurrentHashMap
  • ArrayList: 인덱스 접근이 빠르지만 중간 삽입/삭제 시 요소 이동 비용이 들 수 있다.
  • HashMap: 평균적으로 검색·삽입 O(1), 충돌/리사이징과 키 설계에 주의.
  • ConcurrentHashMap: 동시 접근을 고려한 구현. 여러 연산을 묶은 비즈니스 동작까지 자동으로 원자적으로 만들지는 않는다.

06. interface vs abstract class ★

  • interface: 외부에 제공할 역할/계약. 구현 교체와 느슨한 결합에 유리하다.
  • abstract class: 공통 상태나 구현을 상속으로 공유해야 할 때 사용한다.
  • Spring DI에서는 PaymentClient 인터페이스를 통해 구현체를 교체하거나 테스트 대역을 주입하는 식으로 활용한다.
  • 인터페이스를 무조건 만들기보다 실제 교체 가능성·경계·테스트 필요성을 판단하자.

07. 상속보다 합성을 고려하는 이유 ★★

상속은 부모의 구현과 자식 사이의 결합이 강해질 수 있다. 합성(composition)은 필요한 역할의 객체를 필드로 보유하고 위임하므로 변경에 유연하다. DI는 이러한 합성 구조를 편하게 구성하도록 돕는다.

08. final, static, 불변 객체 ★

  • final 변수: 재할당 방지(참조 대상 객체의 내부 상태가 반드시 불변인 것은 아님).
  • static: 인스턴스가 아닌 클래스에 소속된 멤버.
  • 불변 객체: 생성 후 관찰 가능한 상태가 바뀌지 않도록 설계한 객체. 동시성·테스트 측면에서 유리하다.
  • record: Java의 불변 데이터 전달 객체를 간결하게 정의할 때 유용하지만, 참조하는 내부 객체까지 깊은 불변성을 보장하지는 않는다.

09. Checked vs Unchecked Exception ★★

구분 예 특징
Checked IOException 컴파일러가 처리 또는 선언을 요구
Unchecked NullPointerException, IllegalArgumentException RuntimeException 계열, 처리 강제 없음

Spring 연결: 기본 @Transactional 롤백 정책은 RuntimeException 및 Error에 반응한다. Checked Exception에는 기본적으로 롤백하지 않으므로 설정을 확인해야 한다.

10. Generics, Stream, Optional ★

  • Generics: 컴파일 시점 타입 안정성과 불필요한 캐스팅 감소.
  • Stream: 컬렉션 연산을 선언적으로 표현. 중간 연산은 지연 실행되고 최종 연산이 실행을 시작한다. 모든 경우에 빠른 것은 아니다.
  • Optional: 값 부재를 명시. 주로 반환값에서 사용하며 무분별한 필드/파라미터 사용은 피한다.

11. Thread, Race Condition, synchronized ★★

  • 프로세스는 실행 중인 프로그램, 스레드는 프로세스 내부 실행 흐름이다.
  • 여러 스레드가 공유 상태를 동시에 바꾸면 경쟁 조건(race condition) 이 생길 수 있다.
  • synchronized는 모니터 락과 가시성 보장을 제공하지만 경쟁·병목·데드락 설계에 주의.
  • 중요: Spring의 기본 singleton Bean은 여러 요청 스레드에서 공유될 수 있다. 따라서 상태 없는(stateless) Service를 기본으로 설계한다.

Part 2. Spring Core: 가장 중요한 구간

12. Spring Framework vs Spring Boot ★

  • Spring Framework: IoC 컨테이너, DI, AOP, MVC, 트랜잭션 등 애플리케이션 기반 기능을 제공한다.
  • Spring Boot: Spring 기반 애플리케이션의 설정과 실행을 간소화한다. 자동 설정, Starter 의존성, 내장 서버, 운영 기능 등을 제공한다.
  • Boot가 Spring을 대체하는 것은 아니다. Boot는 Spring Framework를 더 편하게 사용하게 해주는 계층이다.

면접 답변: “Spring은 핵심 기능을 제공하는 프레임워크이고, Boot는 의존성과 설정을 자동화해 Spring 앱을 빠르게 구성·실행하게 해줍니다.”

13. IoC: 제어의 역전 ★★★

기존 방식에서는 개발자 코드가 필요한 객체를 직접 생성하고 연결한다. IoC에서는 객체의 생성·조립·생명주기 제어를 컨테이너에 맡긴다.

직접 생성: OrderService가 new PaymentClient()를 호출
IoC 방식: Spring이 PaymentClient를 만들고 OrderService에 연결

핵심: IoC는 상위 개념이고 DI는 이를 실현하는 대표 방식이다.

14. DI: 의존성 주입 ★★★

객체가 의존 대상을 내부에서 직접 생성하지 않고 외부로부터 전달받는 설계다.

  • 생성자 주입: 필수 의존성이 생성 시 확정된다. 불변성·테스트 용이성·누락된 의존성 조기 발견에 유리하다.
  • Setter 주입: 선택적이거나 변경 가능한 의존성에 쓰일 수 있다.
  • 필드 주입: 간결하지만 테스트·불변성·일반 Java 생성에서 불리하여 보통 지양한다.
  • 생성자가 하나뿐인 Bean에서는 생성자 @Autowired를 생략할 수 있다.

면접 답변: “DI는 필요한 객체를 외부에서 주입하는 방식입니다. 구현체 생성 책임을 분리해 결합도를 낮추고 테스트 대역으로 교체하기 쉽게 만듭니다.”

15. Bean과 ApplicationContext ★★★

  • Bean: Spring IoC 컨테이너가 관리하는 객체. 모든 Java 객체가 Bean인 것은 아니다.
  • BeanFactory: Bean 조회·생성 등 핵심 컨테이너 기능.
  • ApplicationContext: BeanFactory 기능에 더해 이벤트, 메시지, 리소스 및 애플리케이션 통합 기능을 제공하는 상위 컨테이너 인터페이스.
  • 컨테이너는 Bean 정의를 읽고 생성, 의존성 주입, 초기화, 종료 등을 관리한다.

16. Bean 등록 방법 ★

방법 주로 쓰는 경우
@Component 일반 컴포넌트 자동 탐색
@Service 비즈니스 서비스 역할 표시
@Repository 영속성 계층 역할 표시; 예외 변환도 연계 가능
@Controller / @RestController 웹 요청 처리
@Bean + @Configuration 외부 라이브러리 객체, 명시적 구성

@Service와 @Repository는 @Component의 특화된 스테레오타입이다. @Bean은 메서드 반환 객체를 컨테이너에 등록한다.

17. @ComponentScan과 Bean 충돌 ★★

  • 컴포넌트 스캔은 기준 패키지 및 하위 패키지에서 후보를 탐색한다.
  • 같은 타입 구현이 여러 Bean이면 주입 후보가 모호해질 수 있다.
  • 해결 수단: @Qualifier, @Primary, 명시적인 Bean 이름, 컬렉션 주입 등.
  • 함정: @Primary가 붙으면 무조건 모든 위치에서 우선하는 것은 아니다. 특정 @Qualifier 등 더 명시적인 조건이 영향을 준다.

18. Bean Scope & Lifecycle ★★

  • singleton(기본): 컨테이너당 해당 Bean 정의의 인스턴스를 보통 하나 유지. 애플리케이션 전체에서 절대 하나라는 뜻은 아님.
  • prototype: 조회할 때마다 새 인스턴스를 제공. 생성·초기화 이후의 전체 종료 관리는 일반적으로 컨테이너가 수행하지 않는다.
  • 웹 환경의 request, session scope도 있다.
  • 전형적 생명주기: Bean 생성 → 의존성 주입 → 초기화 콜백 → 사용 → 종료 콜백.
  • 초기화/종료: @PostConstruct, @PreDestroy 또는 @Bean(initMethod=..., destroyMethod=...) 등.

19. 순환 참조 ★★

Service A가 B를 주입받고 B도 A를 주입받는 경우다. 생성자 주입에서는 일반적으로 생성할 수 없어 오류가 발생한다. @Lazy 등으로 억지 해결하기 전에 책임 분리·의존 방향을 먼저 검토한다.

20. AOP와 Proxy ★★★

  • AOP: 핵심 비즈니스 코드와 여러 곳에서 반복되는 횡단 관심사(트랜잭션·로깅·권한 등)를 분리한다.
  • Proxy: 대상 객체를 감싸 호출 전후에 부가 동작을 실행하는 객체다.
  • Spring AOP는 기본적으로 프록시 기반이다. JDK 동적 프록시와 클래스 기반 프록시가 대표적이다.
  • Advice는 수행할 부가 동작, Pointcut은 적용할 지점 조건을 뜻한다.
Controller → Service Proxy → [트랜잭션 시작] → 실제 Service → [커밋/롤백]

자주 틀리는 질문: “같은 클래스에서 this.save()를 호출하면 save()의 @Transactional이 동작하나요?”
답: 기본 프록시 방식에서 그 내부 호출은 프록시를 통과하지 않아, 그 호출만으로 save()에 선언된 트랜잭션 경계가 새로 적용되지 않는다. 이미 바깥쪽에서 시작한 트랜잭션이 있다면 그 트랜잭션은 유지될 수 있다. AspectJ 모드는 별도다.

21. Spring Boot 자동 설정 ★★★

  • Boot는 클래스패스, 설정값, 기존 Bean 존재 여부 등을 조건으로 Bean 설정을 적용한다.
  • @SpringBootApplication은 일반적으로 @SpringBootConfiguration, @EnableAutoConfiguration, @ComponentScan을 묶는다.
  • @ConditionalOnClass, @ConditionalOnMissingBean 같은 조건 개념을 이해하자.
  • 특정 자동 설정을 제외할 수 있고, 디버그 조건 평가 보고서로 왜 적용됐는지 확인할 수 있다.
  • 오해: “Boot는 모든 걸 자동으로 만든다” → 조건에 맞는 설정을 적용하며 사용자 Bean이 우선할 수도 있다.

22. 설정 주입과 Profile ★

  • application.yml/.properties: 환경설정.
  • @Value: 단순 설정값 주입.
  • @ConfigurationProperties: 관련 설정을 타입 안전하게 묶어 바인딩.
  • @Profile: 특정 환경의 Bean 구성을 선택.
  • 암호/토큰은 코드나 저장소에 직접 넣지 않고 적절한 비밀 관리 수단을 쓴다.

Part 3. Spring MVC: HTTP 요청의 실제 경로

23. Servlet과 DispatcherServlet ★★★

  • Servlet: Java 웹 요청과 응답을 처리하는 서버 측 구성요소.
  • DispatcherServlet: Spring MVC의 Front Controller. 요청을 받아 적절한 핸들러로 연결한다.
클라이언트
  → Servlet Filter / Spring Security
  → DispatcherServlet
  → HandlerMapping(요청 처리 대상 선택)
  → HandlerAdapter(대상 호출)
  → Controller
  → Service → Repository → DB
  → 반환값 처리(메시지 컨버터 등) → HTTP 응답

면접 답변: “Spring MVC는 DispatcherServlet을 중심으로 요청을 처리합니다. HandlerMapping이 핸들러를 찾고 HandlerAdapter가 호출을 맡으며, 컨트롤러 반환값은 메시지 컨버터 등을 거쳐 응답이 됩니다.”

24. Controller → Service → Repository ★★★

계층 책임 하지 않는 편이 좋은 일
Controller HTTP 입출력, DTO 검증, 응답 코드 복잡한 비즈니스 규칙, 직접 SQL 처리
Service 업무 흐름과 규칙, 트랜잭션 경계 HTTP 세부사항에 과도하게 결합
Repository/Mapper 데이터 조회·저장, DB 추상화 화면 표현이나 요청 응답 정책

3계층은 무조건 세 클래스를 만들라는 규칙이 아니라 변경 이유를 분리하기 위한 구조다.

25. @Controller vs @RestController ★

  • @Controller: 주로 MVC View를 반환하거나 @ResponseBody로 본문을 반환.
  • @RestController: @Controller + @ResponseBody로, 반환값을 기본적으로 HTTP 응답 본문에 직렬화.
  • JSP 기반 프로젝트에서는 View 렌더링, Next.js 연계 API에서는 JSON 응답이라는 맥락을 예로 설명하면 좋다.

26. 주요 요청 어노테이션 ★

어노테이션 쓰임
@GetMapping, @PostMapping 등 HTTP 메서드와 경로 매핑
@PathVariable URL 경로 변수
@RequestParam 쿼리/폼 파라미터
@RequestBody 요청 본문을 객체로 역직렬화
@Valid / @Validated 입력값 검증
@RequestHeader 헤더 추출
ResponseEntity 상태 코드·헤더·본문 제어
@ControllerAdvice / @RestControllerAdvice 공통 예외 처리

27. Filter vs Interceptor vs AOP ★★

구분 실행 위치 대표 용도
Filter Servlet 레벨, DispatcherServlet 앞쪽 보안 필터, 인코딩, 요청 래핑
Interceptor Spring MVC 핸들러 호출 전후 MVC 인증 보조, 요청 로깅, 공통 모델
AOP Spring이 관리하는 메서드 호출 지점 트랜잭션, 메서드 단위 공통 로직

주의: 보안의 핵심 인증·인가를 임의 Interceptor 하나로 대체하려는 설계는 신중해야 한다. Spring Security 필터 체인과 권한 정책을 활용하는 것이 일반적이다.

28. REST, HTTP 상태 코드, 멱등성 ★★

  • GET: 리소스 조회, 안전(safe)하며 멱등적.
  • PUT: 대상 리소스를 지정한 표현으로 대체하는 의미, 멱등적.
  • PATCH: 부분 변경. PATCH는 항상 멱등적인 것은 아니다.
  • DELETE: 삭제 요청은 의미상 멱등적. 반복했을 때 응답 상태 코드는 달라질 수 있다.
  • POST: 리소스 생성 또는 동작 실행. 일반적으로 멱등성을 보장하지 않는다.
  • 200 OK, 201 Created, 204 No Content, 400 Bad Request, 401 Unauthorized(인증 필요), 403 Forbidden(권한 부족), 404 Not Found, 409 Conflict, 500 Internal Server Error의 의미를 설명해 보자.

29. DTO와 Entity를 분리하는 이유 ★★

API 입출력 형식과 영속성 모델의 변화 이유가 다르기 때문이다. API 응답에 Entity를 직접 내보내면 내부 필드 노출, 관계 순회, 직렬화 문제와 스키마 결합이 생길 수 있다. 단, 모든 DTO를 형식적으로 복제할 필요는 없고 경계와 요구사항에 따라 판단한다.

Part 4. 트랜잭션·DB: 경력직 면접의 중심

30. 트랜잭션과 ACID ★★★

트랜잭션은 여러 데이터 작업을 하나의 일관된 업무 단위로 처리하기 위한 경계다.

속성 뜻 예
Atomicity(원자성) 모두 성공하거나 전체 취소 이체의 출금·입금
Consistency(일관성) 제약과 규칙 유지 잔액·무결성 제약
Isolation(격리성) 동시 트랜잭션 간 간섭 제어 같은 계좌 동시 수정
Durability(지속성) 커밋 결과 유지 장애 후 복구

실무 질문: “마이그레이션 1만 건을 한 트랜잭션으로 묶으면 어떤 문제가 있을까요?”
→ 락 유지, Undo/로그·메모리·리소스 압박, 긴 롤백 시간 등을 고려해 업무적 원자성 기준과 배치 크기를 설계해야 한다.

31. @Transactional 동작 원리 ★★★

  1. 트랜잭션이 적용된 Spring Bean의 메서드를 프록시를 통해 호출한다.
  2. 프록시의 트랜잭션 인터셉터가 설정을 해석한다.
  3. 트랜잭션 매니저가 기존 트랜잭션 참여 또는 새 트랜잭션 시작을 결정한다.
  4. 실제 메서드가 실행된다.
  5. 결과와 롤백 규칙에 따라 커밋 또는 롤백한다.

핵심 주의점:

  • 기본 프록시 모드에서 this.method() 내부 호출은 새로운 @Transactional 경계로 가로채지지 않는다.
  • 기본 롤백: RuntimeException, Error에 롤백. Checked Exception은 기본적으로 롤백하지 않는다. rollbackFor 등으로 변경 가능.
  • 예외를 catch한 뒤 정상 반환하면 트랜잭션 인터셉터는 그 예외를 모를 수 있다.
  • readOnly=true는 최적화 힌트/설정이지, 모든 DB 쓰기를 물리적으로 막는 보편적 보안 장치가 아니다.
  • 트랜잭션 내부에서 긴 외부 API 호출을 하면 DB 연결·락을 오래 점유할 수 있다.

32. Propagation ★★★

옵션 핵심 동작 주의점
REQUIRED(기본) 기존 트랜잭션 참여, 없으면 생성 내부 실패가 전체에 영향
REQUIRES_NEW 기존 것을 중단하고 별도 트랜잭션 실행 추가 연결·독립 커밋 고려
SUPPORTS 있으면 참여, 없으면 비트랜잭션 실행 읽기 전용이라고 보장되는 건 아님
MANDATORY 기존 트랜잭션 없으면 오류 외부 트랜잭션 경계 필수
NOT_SUPPORTED 트랜잭션 없이 실행 기존 트랜잭션 일시 중단
NEVER 트랜잭션이 있으면 오류 특별한 제약 용도
NESTED 지원 환경에서 저장점 기반 중첩 DB/트랜잭션 매니저 지원 확인

면접 함정: REQUIRES_NEW 안에서 커밋한 기록은 바깥 트랜잭션이 나중에 롤백되더라도 보통 그대로 유지된다. 구현·데이터소스 설정을 확인해야 한다.

33. Isolation Level ★★★

수준 대표적으로 막는 현상 생각할 점
READ UNCOMMITTED 격리 보장이 낮음 Dirty read 가능
READ COMMITTED Dirty read Non-repeatable read 가능
REPEATABLE READ 같은 행의 반복 읽기 안정성 강화 DB의 MVCC·락 구현 차이
SERIALIZABLE 가장 강한 직렬 실행에 가까운 보장 성능·충돌 비용

중요: Phantom read, 갱신 충돌 등의 실제 동작은 DB 구현과 락/MVCC 방식에 따라 달라진다. Oracle과 MySQL의 기본 격리 수준도 같다고 가정하지 말 것.

34. JDBC vs MyBatis vs JPA ★★★

항목 JDBC MyBatis JPA(예: Hibernate)
개발 관점 SQL·연결·매핑을 직접 다룸 SQL 중심 매퍼 객체와 영속성 모델 중심
SQL 제어 매우 직접적 매우 직접적 JPQL/Criteria/네이티브 SQL 가능
편의 기능 낮은 수준 API SQL 매핑 지원 영속성 컨텍스트, 변경 감지 등
주의점 보일러플레이트 SQL·매핑 관리 비용 N+1, 상태·Flush 이해 필요

판단 예시: 복잡한 금융권 조회 SQL·PL/SQL, 레거시 DB 구조에는 MyBatis가 실용적일 수 있다. 도메인 객체의 상태 변경과 관계 탐색이 많은 애플리케이션에는 JPA가 유리할 수 있다. 둘 다 사용할 수 있고, 팀 역량·쿼리 복잡도·운영 환경을 보고 결정한다.

35. JPA 영속성 컨텍스트와 Dirty Checking ★★★

  • EntityManager / Persistence Context: 영속 상태의 Entity를 관리하는 문맥.
  • 1차 캐시: 같은 영속성 컨텍스트에서 엔티티 식별자 기반 중복 조회를 줄일 수 있다.
  • Dirty Checking: 영속 Entity 변경을 감지해 Flush 시 SQL 반영을 준비한다.
  • Flush: 영속성 컨텍스트의 변경을 DB SQL에 반영하는 과정. 커밋과 동일하지 않다.
  • Detach: 영속성 컨텍스트에서 분리되면 변경 감지 대상이 아니다.

36. N+1 문제 ★★★

목록을 1번 조회했지만 각 행의 연관 데이터를 다시 조회하면서 추가 N번 SQL이 발생하는 문제다.

주문 100건 조회: 1회
각 주문의 회원 조회: 최대 100회
총 101회 SQL → 지연시간 증가

해결 후보: Fetch Join, EntityGraph, 배치 페치, 필요한 컬럼만 Projection, 조회 쿼리 분리 등. 단순히 모든 관계를 EAGER로 바꾸는 것은 일반적 해결책이 아니다.

37. Connection Pool ★★

DB 연결은 생성 비용이 높아 풀에서 재사용한다. HikariCP가 대표적이다.

  • Pool 크기를 무조건 키우면 DB 동시 처리 한도·락 경합·자원 압박이 커질 수 있다.
  • 커넥션 반환 누락, 느린 SQL, 긴 트랜잭션, 외부 API 대기 등은 풀 고갈을 유발한다.
  • 조사 순서: 활성/대기 커넥션 수 → 느린 트랜잭션과 쿼리 → 타임아웃 → DB 세션/락.

38. Index, 실행 계획, 페이징 ★★★

  • 인덱스: 검색 경로를 줄일 수 있는 자료구조. 쓰기 비용·공간 비용이 따른다.
  • WHERE 조건, 조인, 정렬, 선택도, 복합 인덱스 컬럼 순서가 중요하다.
  • 느린 SQL을 보면 실행 계획(Explain Plan) 과 실제 처리 행 수, 인덱스 사용, 정렬·스캔을 확인한다.
  • OFFSET 페이징은 깊은 페이지에서 비용이 커질 수 있어 커서/Keyset 페이징을 검토한다.

39. 락과 동시성 제어 ★★★

  • 낙관적 락: 충돌이 적다고 가정하고 버전 값(@Version 등)으로 갱신 충돌 검출.
  • 비관적 락: 수정 대상에 DB 락을 걸어 동시 변경을 제어.
  • Lost Update: 두 요청이 같은 값을 읽고 덮어쓰는 문제.
  • Deadlock: 서로 필요한 락을 기다려 진행하지 못하는 상태.
  • 수단 선택은 충돌 빈도, 처리량, 사용자 경험, 재시도 가능성에 달렸다.

Part 5. Spring Security: 인증·인가를 구분하자

40. 인증(Authentication) vs 인가(Authorization) ★★★

  • 인증: “누구인가?”를 확인(로그인, JWT 검증 등).
  • 인가: “이 리소스에 접근해도 되는가?”를 판단(역할·소유권·정책).

예: 로그인에 성공한 일반 회원도 다른 사람의 급여 정보에는 접근할 수 없어야 한다. 인증 성공만으로 인가가 끝나지 않는다.

41. SecurityFilterChain ★★★

  • Spring Security의 Servlet 지원은 FilterChainProxy와 그 안의 SecurityFilterChain을 통해 필터들을 실행한다.
  • 인증 필터가 사용자 신원을 확인하고, SecurityContext에 인증 결과를 보관하며, 인가 단계에서 정책을 판단한다.
  • 필터 순서는 중요하다. 다수의 체인이 있다면 어떤 요청에 매칭되는지도 확인해야 한다.
  • 최신 방식에서는 일반적으로 SecurityFilterChain Bean으로 보안 정책을 구성한다.

42. Session/Cookie vs JWT ★★

항목 서버 세션 방식 JWT 기반 방식
상태 서버가 세션 상태 관리 토큰 자체에 서명된 Claim을 담을 수 있음
클라이언트 보관 보통 세션 ID 쿠키 쿠키 또는 헤더 등
폐기 서버 세션 무효화 가능 발급 후 즉시 폐기에 별도 전략 필요
주요 위험 세션 탈취·CSRF 등 토큰 탈취, 저장 위치, 갱신·폐기 전략

주의: JWT를 쓴다는 사실만으로 시스템이 완벽한 무상태(stateless) 또는 안전한 구조가 되는 것은 아니다. Refresh Token 관리, 키 회전, 만료 시간, HTTPS, 로그아웃 정책까지 설계해야 한다.

43. 비밀번호 처리 ★

비밀번호는 복호화 가능한 암호화로 보관하기보다 안전한 비밀번호 해시(예: BCrypt/Argon2 등)로 검증한다. 평문 저장·직접 만든 해시 알고리즘은 피한다.

44. CORS vs CSRF ★★★

  • CORS: 브라우저가 다른 출처의 응답을 JavaScript에서 읽을 수 있는지에 관한 정책. 서버 접근 제어 전체를 대체하지 않는다.
  • CSRF: 사용자의 인증 상태를 악용해 원치 않는 요청을 보내게 하는 공격.
  • 쿠키 기반 인증에서 CSRF 방어를 특히 검토한다. Authorization 헤더에 명시적으로 토큰을 넣는 방식은 위협 모델이 다르지만 무조건 안전하다는 뜻은 아니다.
  • CORS 설정을 했다고 CSRF가 해결되는 것은 아니다.

45. 401 vs 403 ★

  • 401: 유효한 인증 정보가 없거나 인증이 필요함(HTTP 명칭은 Unauthorized).
  • 403: 서버가 요청을 이해했지만 접근을 허용하지 않음.
  • 리소스 존재 여부를 감추기 위해 404를 선택하는 설계도 있으므로 실제 정책을 설명할 수 있어야 한다.

Part 6. 실무 설계·테스트·운영

46. 계층 분리와 의존 방향 ★★

Controller는 HTTP를 다루고, Service는 업무 규칙을 다루며, Repository는 DB 접근을 다룬다. 의존성은 가능한 한 업무 규칙이 외부 기술에 덜 묶이게 만든다. 구조보다 중요한 것은 테스트 가능한 책임과 변경 범위다.

47. 단위 테스트 vs 통합 테스트 ★★

  • 단위 테스트: 특정 비즈니스 로직을 외부 의존성 없이 빠르게 검증한다.
  • 통합 테스트: Spring 컨텍스트, DB, HTTP 등 여러 요소가 결합된 동작을 확인한다.
  • @SpringBootTest: 넓은 범위의 애플리케이션 컨텍스트를 사용해 테스트.
  • @WebMvcTest: MVC 관련 구성에 집중한 테스트 슬라이스. Boot 3/4의 모듈·패키지 경로 차이는 버전별 공식 문서 확인.
  • MockMvc: 실제 네트워크 포트를 열지 않고 Spring MVC 요청 처리 테스트 가능.
  • Testcontainers: 테스트용 DB 등 외부 의존성의 실행 환경을 일관되게 마련하는 데 유용.

48. 테스트하기 좋은 코드 ★★

생성자 주입, 작은 메서드, 외부 I/O 추상화, 명확한 입력과 출력이 중요하다. 비즈니스 규칙 테스트에서 매번 DB/서버를 띄워야 한다면 책임 분리를 검토할 신호다.

49. 성능 장애 진단 기본 순서 ★★★

  1. 증상 수집: 응답 시간(P50/P95/P99), 오류율, 처리량, 시간대.
  2. 범위 좁히기: 요청 추적 → 애플리케이션 로그 → DB SQL/풀 → 외부 API.
  3. 자원 확인: CPU, 힙/GC, 스레드, 커넥션, 락, 디스크.
  4. 가설 세우기: N+1, 인덱스 부재, 커넥션 고갈, 메모리 증폭, 락 경합.
  5. 검증·수정: 재현 → 단일 원인 검증 → 부하/회귀 테스트 → 모니터링.

50. 캐시 ★★

  • 캐시는 자주 쓰는 데이터를 빠르게 제공하지만 무효화와 일관성 문제가 따라온다.
  • Local cache와 Redis 같은 분산 캐시의 공유 범위가 다르다.
  • TTL, 갱신, 캐시 키, 동시 요청(Cache Stampede)을 설계해야 한다.
  • 데이터가 자주 변하거나 정확한 최신값이 필수라면 캐시를 신중하게 적용한다.

51. @Async, 스케줄러, 메시지 큐 ★★

  • @Async: 별도 실행 흐름에 작업을 위임한다. 실행기, 트랜잭션/보안 컨텍스트 전파, 예외 처리를 고려한다.
  • 스케줄러: 정해진 시점에 작업 실행. 다중 인스턴스에서는 중복 실행 방지 필요.
  • 메시지 큐: 작업을 비동기 분리하고 장애를 완충할 수 있지만 재시도·중복 소비·순서 보장이 별도 설계 대상이다.
  • 함정: @Async 역시 프록시 기반 호출 조건을 고려해야 한다.

52. 관측 가능성 ★★

  • 로그: 무슨 일이 있었는가?
  • 메트릭: 얼마나 자주, 얼마나 느리게, 얼마나 많이 발생하는가?
  • 트레이스: 한 요청이 여러 구성요소를 지나간 경로는?
  • 개인정보·토큰·비밀번호를 로그에 남기지 않는다.

10-4. Entity: JPA가 관리하는 객체와 상태 전이

src/main/java/dev/study/taskboard/task/Task.javajava
package dev.study.taskboard.task;

import jakarta.persistence.*;
import java.time.Instant;

@Entity
@Table(name = "tasks")
public class Task {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 100)
    private String title;

    @Column(length = 1000)
    private String description;

    @Column(nullable = false)
    private boolean completed;

    @Version
    private long version; // 동시 수정 충돌을 탐지하는 낙관적 락 버전

    @Column(nullable = false, updatable = false)
    private Instant createdAt;

    @Column(nullable = false)
    private Instant updatedAt;

    protected Task() {} // JPA 프록시 및 엔티티 생성을 위한 생성자

    public Task(String title, String description) {
        this.title = title;
        this.description = description;
        this.completed = false;
    }

    @PrePersist
    void onCreate() {
        createdAt = Instant.now();
        updatedAt = createdAt;
    }

    @PreUpdate
    void onUpdate() {
        updatedAt = Instant.now();
    }

    public void edit(String title, String description) {
        this.title = title;
        this.description = description;
    }

    public void changeCompletion(boolean completed) {
        this.completed = completed;
    }

    public Long getId() { return id; }
    public String getTitle() { return title; }
    public String getDescription() { return description; }
    public boolean isCompleted() { return completed; }
    public long getVersion() { return version; }
    public Instant getCreatedAt() { return createdAt; }
    public Instant getUpdatedAt() { return updatedAt; }
}
코드의미면접에서 추가로 알아야 할 점
@EntityJPA 관리 대상영속/준영속/비영속 상태 구분
@Id + IDENTITY식별자 생성IDENTITY는 ID 확보를 위해 INSERT 시점이 앞당겨질 수 있음
@Version낙관적 잠금동시 갱신 시 버전 충돌을 예외로 탐지
@PrePersist/@PreUpdate엔티티 생명주기 콜백DB 시각과 애플리케이션 시각 정책 차이
protected Task()JPA 객체 생성 지원JPA는 인자가 없는 public/protected 생성자를 요구
edit()상태 변경 행위 캡슐화무분별한 Setter 대신 의도 드러내기
Entity와 DB 테이블이 1:1이라고 단순화하지 말 것
Entity는 영속성에 사용되는 객체이며 연관관계, 값 객체, 상속 매핑 등이 있다. 또한 @Version은 “수정 충돌을 막아주는 마법”이 아니라 충돌을 탐지하고 예외를 발생시킨다. 실제 API에는 충돌 예외를 HTTP 409로 변환하거나 사용자에게 재시도를 안내하는 정책도 필요하다.

import org.springframework.transaction.annotation.Transactional;

@Service
@Transactional(readOnly = true) // 조회 기본값, 쓰기 메서드에서 override
public class TaskService {
    private final TaskRepository repository;

    public TaskService(TaskRepository repository) {
        this.repository = repository; // 생성자 주입: DI
    }

    public Page<TaskResponse> list(Boolean completed, Pageable pageable) {
        Page<Task> tasks = completed == null
                ? repository.findAll(pageable)
                : repository.findByCompleted(completed, pageable);
        return tasks.map(TaskResponse::from);
    }

    public TaskResponse get(Long id) {
        return TaskResponse.from(findTask(id));
    }

    @Transactional
    public TaskResponse create(CreateTaskRequest request) {
        Task task = new Task(request.title(), request.description());
        return TaskResponse.from(repository.save(task));
    }

    @Transactional
    public TaskResponse update(Long id, UpdateTaskRequest request) {
        Task task = findTask(id);
        task.edit(request.title(), request.description());
        // 변경 감지는 flush/commit 시 일어난다. 반환 DTO의 version·updatedAt
        // 최신값을 얻기 위해 명시적으로 flush한다. flush는 commit이 아니다.
        repository.flush();
        return TaskResponse.from(task);
    }

    @Transactional
    public TaskResponse changeCompletion(Long id, CompletionRequest request) {
        Task task = findTask(id);
        task.changeCompletion(request.completed());
        repository.flush();
        return TaskResponse.from(task);
    }

    @Transactional
    public void delete(Long id) {
        Task task = findTask(id);
        repository.delete(task);
    }

    private Task findTask(Long id) {
        return repository.findById(id)
                .orElseThrow(() -> new TaskNotFoundException(id));
    }
}

이 클래스의 주인공은 생성자 주입과 트랜잭션 경계다. 컨테이너는 TaskRepository 구현 프록시를 만들고 TaskService 생성자에 전달한다. 외부에서 TaskService.create()를 호출하면 트랜잭션 프록시를 통과한다. 예외가 없으면 커밋하고 기본적으로 RuntimeException/Error에는 롤백한다. findTask는 private 메서드이므로 별도 트랜잭션 경계를 설정하지 않는다.

특히 update()는 save(task)가 없다. 이미 영속성 컨텍스트가 관리하는 Entity를 변경하고 flush()하면 Hibernate가 스냅샷과 비교하여 SQL UPDATE를 생성한다. 여기서 flush는 commit이 아니다. 이 예제에서 명시적 flush가 필요한 이유는 DB 반영 자체보다 @Version과 @PreUpdate 값이 응답 DTO에 최신값으로 들어가도록 하기 위해서다.

import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

import java.util.LinkedHashMap;
import java.util.Map;

@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler(TaskNotFoundException.class)
    public ProblemDetail notFound(TaskNotFoundException ex) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
                HttpStatus.NOT_FOUND, ex.getMessage());
        problem.setTitle("할 일을 찾을 수 없습니다");
        return problem;
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ProblemDetail invalidRequest(MethodArgumentNotValidException ex) {
        Map<String, String> errors = new LinkedHashMap<>();
        ex.getBindingResult().getFieldErrors().forEach(error ->
                errors.putIfAbsent(error.getField(), error.getDefaultMessage()));
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
                HttpStatus.BAD_REQUEST, "입력 항목을 확인해 주세요");
        problem.setTitle("입력 검증 실패");
        problem.setProperty("errors", errors);
        return problem;
    }
}

@RestControllerAdvice는 여러 Controller의 예외를 한 곳에서 변환한다. ProblemDetail은 HTTP API 오류의 표준화된 표현(RFC 9457)에 맞춘 Spring 타입이다. 이 예제는 검증 오류의 errors 속성을 확장 필드로 제공한다. 예외를 무조건 200으로 반환하거나, 내부 스택 트레이스를 사용자에게 공개하는 구현은 피한다. 예상치 못한 500 오류는 적절히 로깅하되 응답에는 과도한 내부 정보를 노출하지 않는다.

Part 11. 전문가 관점: 왜 이렇게 작동할까?

11-1. 요청 1건이 실제로 지나가는 경로

요청은 메서드를 곧바로 호출하지 않는다. TCP 연결에서 HTTP로 들어온 뒤, Tomcat의 작업 스레드가 서블릿 Filter 체인을 거쳐 DispatcherServlet에 넘긴다. HandlerMapping이 컨트롤러 메서드를 선택하고 HandlerAdapter가 인자 변환/검증/메서드 호출을 수행한다. 응답 객체는 HttpMessageConverter로 JSON 직렬화된다.

POST 요청 흐름text
POST /api/tasks  {"title":"DI 연습"}
   ↓ 1. Tomcat: 연결·스레드 관리
   ↓ 2. Servlet Filter: 공통 보안/로깅 등
   ↓ 3. DispatcherServlet: Front Controller
   ↓ 4. HandlerMapping & HandlerAdapter
   ↓ 5. Jackson(JSON → CreateTaskRequest), @Valid
   ↓ 6. TaskController.create()

   ↓ 11. Jackson(TaskResponse → JSON), HTTP 전송

11-2. DI 컨테이너는 왜 테스트 가능성을 높일까?

동일한 서비스, 서로 다른 구현체java
// Spring 없는 순수 Java: 구현을 직접 생성하면 교체가 어렵다
interface Sender { void send(String message); }
class RealSender implements Sender {
    public void send(String msg) { System.out.println("외부 전송: " + msg); }
}
class NoticeService {
    private final Sender sender;
    NoticeService(Sender sender) { this.sender = sender; }
    void notifyUser() { sender.send("완료"); }
}

// 운영 환경 연결:
NoticeService prod = new NoticeService(new RealSender());
// 테스트 환경 연결:
Sender fake = msg -> System.out.println("가짜 전송: " + msg);
NoticeService test = new NoticeService(fake);

test.notifyUser();  // 외부 전송 없이 검증 가능

핵심은 Spring을 쓰기 전에 의존성 방향을 추상화하는 것이다. Spring DI는 이런 연결을 컨테이너가 수행해 준다. @Service와 생성자를 사용하면 Bean 그래프를 조립하고, 테스트에서는 별도 테스트 Bean 또는 Mock을 주입할 수 있다. Bean이 singleton이어도 요청별 가변 필드를 유지하지 않도록 설계해야 한다.

11-3. 트랜잭션 프록시와 self-invocation 함정

오해를 부르는 self-invocation 코드java
@Service
class BillingService {
    public void pay() {
        // 같은 인스턴스의 메서드 직접 호출 → 프록시를 우회
        this.recordPayment();
    }

    @Transactional
    public void recordPayment() {
        // 직접 호출에서는 이 @Transactional이 새로 적용되지 않을 수 있음
    }
}

// 개선: 트랜잭션 경계를 외부에서 호출하는 public Service 메서드로 두거나
// 별도 Spring Bean으로 분리하여 그 Bean을 주입받아 호출한다.
// 단, pay()에 이미 트랜잭션이 있다면 기존 트랜잭션 안에서 실행될 수 있다.

@Transactional은 어노테이션이 DB를 직접 제어하지 않는다. Spring AOP/TransactionInterceptor가 시작 전 PlatformTransactionManager에서 트랜잭션을 열고, 메서드 실행 후 커밋/롤백을 결정한다. 기본 프록시 방식에서 외부 객체 → 프록시 → 대상 객체 호출만 프록시의 Advice가 적용된다. private/final 메서드, 같은 객체 내부 호출에 적용을 기대하면 장애 원인이 된다. AspectJ weaving 같은 다른 모드에서는 조건이 달라질 수 있다.

11-4. 전파 속성, 커넥션 풀과 REQUIRES_NEW 위험

전파효과실무 주의
REQUIRED기존 트랜잭션 참여, 없으면 생성가장 일반적인 기본값
REQUIRES_NEW기존 트랜잭션 중단하고 독립 경계추가 커넥션 수요·독립 커밋·풀 고갈 위험
SUPPORTS있으면 참여, 없으면 비트랜잭션조회에서 사용해도 readOnly와 혼동 금지
MANDATORY기존 트랜잭션 없으면 예외호출자가 반드시 경계를 관리해야 할 때
NESTED저장점(savepoint) 기반 중첩 가능트랜잭션 관리자/DB 지원 여부에 의존

예: 주문 생성 트랜잭션이 DB 커넥션을 점유한 상태에서 감사 로그를 REQUIRES_NEW로 실행하면 두 번째 커넥션이 필요할 수 있다. 트래픽과 풀 크기를 고려하지 않으면 요청들이 서로 기다리는 문제가 생긴다. 로그를 꼭 남겨야 하는 요구가 있다면 Outbox/Event/별도 Queue와 같은 구조적 대안도 고려한다.

11-5. JPA 상태 전이·flush·commit 차이

영속성 컨텍스트는 관리 중인 엔티티와 DB 작업을 조율하는 단위다. persist 또는 save 이후 영속 상태로 관리될 수 있으며, 조회한 엔티티를 변경하면 변경 감지 결과가 flush에 반영된다. 하지만 flush가 DB 트랜잭션을 확정하진 않는다.

변경 감지 → flush → commitjava
@Transactional
public void rename(Long id, String newTitle) {
    Task task = repository.findById(id).orElseThrow(); // 영속 상태
    task.edit(newTitle, task.getDescription());        // 아직 SQL 실행과 별개
    repository.flush();                                // UPDATE SQL 동기화
    // 여기서 RuntimeException 발생 시 트랜잭션 전체 롤백 가능
} // 정상 종료 시 commit: DB 변경 확정

N+1은 연관 엔티티를 각각 조회하면서 추가 SQL이 발생하는 현상이다. FetchType.EAGER로 바꿨다고 항상 해결되는 문제가 아니다. 상황별로 fetch join, @EntityGraph, DTO 프로젝션, 배치 fetch, 조회 전용 쿼리를 선택하고 실제 쿼리 수와 결과를 확인해야 한다. 페이징과 컬렉션 fetch join을 함께 사용하면 DB 페이징이 제한되거나 메모리 페이징 문제가 생길 수 있다.

11-6. 동시성: @Version과 재고 차감은 다르다

조건부 UPDATE를 이용한 원자적 차감의 예sql
// 사용 예시: 재고 차감을 원자적으로 실행하는 SQL
UPDATE product_stock
SET quantity = quantity - :amount
WHERE product_id = :id
  AND quantity >= :amount;

-- affected rows = 1 → 성공, 0 → 재고 부족 또는 ID 없음
-- 단, DB 격리 수준/경합/트랜잭션 의미는 추가 검증 필요.

낙관적 락은 충돌을 낙관적으로 가정하여 버전을 검증하고 실패 시 재시도/409로 처리하는 방식이다. 비관적 락은 SELECT FOR UPDATE 등으로 선점 잠금을 사용한다. 주문/재고에는 재시도 중복 처리와 외부 결제 호출의 멱등성도 함께 설계해야 한다. Redis 분산락만 붙이면 해결되는 문제가 아니며 최종 DB 제약/원자적 갱신이 중요하다.

11-7. Page vs Slice vs 커서 기반 페이징

Page<T>는 목록과 전체 건수를 제공하고 Count Query가 추가될 수 있다. Slice<T>는 다음 페이지 유무를 중심으로 전체 건수 비용을 피할 때 쓴다. Offset pagination은 뒤쪽 페이지의 탐색 비용과 데이터 갱신 중 중복/누락을 주의해야 한다. Keyset/Cursor는 예를 들어 (created_at, id)를 안정 정렬 키로 사용해 무한 스크롤을 구현한다. 정렬 키가 유일하지 않으면 행 중복/누락이 발생할 수 있다.

11-8. Spring Security: 인증과 인가, Filter Chain

보안은 Controller 이전 단계의 SecurityFilterChain을 통해 처리된다. 인증은 누구인지 확인하는 것, 인가는 해당 리소스를 볼 권한이 있는지 확인하는 것이다. 로그인 성공만으로 다른 사용자의 Task 수정 권한이 자동으로 생기지는 않는다. 실무에서는 인증 주체의 userId와 Task 소유자 검증을 반드시 Service 쪽 업무 규칙으로 연결해야 한다.

11-9. 스레드와 Connection Pool을 같이 보는 법

Spring MVC는 일반적으로 요청당 서버 작업 스레드가 동기적으로 흐른다. JDBC 쿼리 실행 중 DB 연결을 기다리는 시간은 응답 지연으로 이어진다. Tomcat worker threads와 HikariCP connections는 별도 리소스이며 DB가 버틸 수 있는 연결 수보다 풀을 무작정 크게 하는 것이 해결책은 아니다. CPU, 응답 지연, 쿼리 실행 계획, Pool active/idle/pending, GC, thread dump와 DB lock wait를 함께 본다.

11-10. 운영 준비: Flyway·Profile·로깅·테스트 전략
